# Обновление пользовательской сессии Checklist: проект решения

Статус: **design only, требуется review; runtime не реализован**. Issue [#21](https://github.com/stammendr1510-oss/KD-Checker/issues/21).
Дата проверки публичной документации: 14.11.2026. База исследования: main `af3ecf5` после PR #20; усиление Content-Range сохраняется и не заменяется этим проектом.

## Границы и рекомендация

Цель следующего этапа — читать актуальный Checklist без ручной замены короткоживущего JWT, сохраняя идентичность пользователя и его RLS-права. Этот PR добавляет только документ, изолированную чистую модель в `design/` и синтетические тесты. Модель не импортируется приложением, не содержит credential API и не умеет обращаться к сети, окружению, хранилищу или Supabase. Проверенные флаги модели — предположения, а не реализация проверки прав.

Рекомендуемый начальный вариант после review — **интерактивная реавторизация по требованию**. Автоматическое серверное обновление на ПК пользователя допустимо рассматривать только после проверки защищённого хранилища, привязки пользователя, межпроцессной сериализации, crash recovery и актуальности прав. До выполнения этих условий функция выключена, текущий способ настройки не меняется. Этот документ не разрешает вход в реальный проект или развёртывание.

Никаких изменений EPLAN Checklist, Supabase Auth, RLS, таблиц, grants, политик, настроек JWT, схемы SQLite, локальной `KD-Checker-v0.7-stable` или ветки main. Не требуется миграция. Текущие проверки КД, статусы инженеров, журнал, CSV/XLSX и исторические снимки остаются прежними. Реальные КД, идентификаторы пользователей, пароли, access/refresh credentials не нужны ни для разработки, ни для CI.

## Проверенные исходные ограничения

`checklist_supabase.py` выполняет GET `public.items` с вложенными `sections` через Data API, используя publishable key и JWT пользователя. `checklist_run.py` при отказе возвращает `unavailable`, а не последний удачный снимок. Существующие проверки URL, запрет редиректов, ограничения размера, Content-Range, количества, связности sections и нормализация снимка обязательны и для будущего адаптера. Успех обновления авторизации сам по себе не означает успешное получение Checklist.

Актуальные официальные источники (чтение публичной документации, без входа в Supabase):

- [Auth sessions](https://supabase.com/docs/guides/auth/sessions): access JWT краткоживущий; refresh credential ротируется. Есть документированные исключения повторного использования: окно по умолчанию 10 секунд и обработка родителя текущего активного refresh credential. За пределами исключений возможен отзыв всей сессии. Наш протокол не использует исключения как разрешение на повтор после неопределённого исхода. Выход не гарантирует немедленную невалидность уже выданного JWT. Встроенные ограничения времени сессии, неактивности и single-session относятся к Pro и выше; их не предлагаем включать.
- [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security): `authenticated` не доказывает квалификацию пользователя. `user_metadata` редактируется пользователем и не является источником полномочий; данные полномочий внутри JWT могут устареть до обновления JWT. Текущие RLS-политики не ослабляются.
- [getUser](https://supabase.com/docs/reference/javascript/auth-getuser) обращается к Auth для проверки пользователя; [getClaims](https://supabase.com/docs/reference/javascript/auth-getclaims) может проверять подпись через кэшированный JWKS. Ни одну операцию не считаем универсальным доказательством текущего членства, отсутствия отзыва сессии и полномочий в приложении.
- [Pricing](https://supabase.com/pricing): бесплатные Auth/Data API доступны в пределах Free-квот. Это не подтверждает тариф, остаток квот или настройки действующего проекта. В этом PR не выполняются запросы к проекту и не расходуются его квоты.
- [Changelog](https://supabase.com/changelog.md) проверен; [отказ от CBC TLS ciphers](https://supabase.com/changelog/cbc-tls-ciphers-deprecated) требует современного TLS-клиента. Не допускается отключать TLS verification или включать слабый fallback ради подключения.

Версии SDK/CLI не меняются; зависимости не добавляются. Перед реализацией необходимо повторно проверить источники: поведение сервиса и тарифы могут измениться.

| --- | --- | --- | --- | --- |
| A. Локальный backend на ПК, отдельная пользовательская сессия, защищённое хранилище | Только доверенный локальный процесс; refresh через Auth, атомарная запись ротированной пары в OS vault; браузер не получает credentials | Возможно периодическое получение без ручной замены JWT | Нужны надёжная идентичность пользователя, vault, межпроцессная блокировка, fencing, recovery и подтверждение текущих прав; отсутствуют в текущем адаптере | Условный целевой вариант автоматизации, заблокирован до отдельного review и проверок |
| B. Реавторизация по требованию | При истечении/неопределённости прекращаем чтение; инженер проходит разрешённый интерактивный вход; новую сессию устанавливает доверенный backend | Меньше долговременных секретов и сложных гонок; можно не сохранять refresh credential между запусками | Требует участия инженера; способ входа, callback/CSRF/PKCE и привязка браузера ещё должны быть спроектированы, без сбора пароля приложением | Предпочтительная первая реализация после review; сейчас не внедряется |
| C. Отдельный read-only endpoint | Только после явного согласия владельца; аутентифицированный endpoint передаёт пользовательский контекст и сохраняет RLS | Можно централизовать контракт чтения | Новая поверхность атаки, эксплуатация и неопределённая стоимость; общий backend-секрет не подтверждает права пользователя | Не вводить сейчас; отдельный проект/согласование, без открытого endpoint и без bypass RLS |

Постоянный JWT в env не решает истечение, ротацию, отзыв или изоляцию пользователей. Общий refresh credential между людьми/ПК смешивает сессии, затрудняет отзыв и аудит и создаёт гонки ротации. Publishable key идентифицирует проект, но не заменяет пользовательскую авторизацию. Service-role/secret key, общая техническая учётная запись, анонимная policy, `SECURITY DEFINER` и публичный прокси не являются допустимыми обходами. Вариант C также не разрешает их.

**Ограничение стоимости:** не активировать Pro, платные session controls, SSO, SMS, сторонние vault/cron/облачные функции или иные платные функции/кредиты. Кандидат A/B использует только проверенные бесплатные возможности Auth/Data API и локальные средства ОС. Перед будущим подключением владелец подтверждает допустимый бесплатный бюджет и отсутствие списаний; при невозможности подтвердить — оставить выключенным. Бесплатность текущего live-проекта не исследовалась. Этот этап не создаёт проектов, функций, пользователей или сессий и не выполняет live refresh/GET. Существующий публичный GitHub Actions workflow используется без новых сервисов, тарифов или расширения матрицы.

## Границы доверия и привязка идентичности

Будущий локальный backend — единственный держатель credentials. Браузер, PDF, пользовательский текст, параметры HTTP, история SQLite, журнал и отчёты считаются недоверенными источниками полномочий. Перед любыми session endpoints нужно защитить локальный интерфейс от чужого пользователя, CSRF и посторонних origins; нельзя превратить нынешнее локальное приложение в multi-user систему добавлением глобального SDK-клиента.

Ключ координатора: **проект + верифицированный subject пользователя + Auth session + локальный пользователь ОС/устройство**. Не принимать `user_id`, `session_id` или project URL из тела запроса как доказательство идентичности. Каждый ПК получает собственную сессию через разрешённую авторизацию; credentials не синхронизируются через файлы, браузерное хранилище, Git или SQLite. В общем серверном процессе нужны изолированные контексты на каждого аутентифицированного клиента; одного module-global session client недостаточно.

Членство в организации Supabase Dashboard и право квалифицированного пользователя в EPLAN Checklist — разные понятия. Подпись JWT, `authenticated`, успех refresh, GET 200 или пустой список не доказывают актуальное право на полный Checklist. Требуется согласованный владельцем источник актуального членства/полномочий, уже разрешённый существующей моделью доступа. Не предлагать новые grants к `auth.sessions`, Admin API или новую policy ради этой проверки.

**Блокирующий вопрос:** текущий доступный контракт может не давать доказательства немедленного отзыва сессии или потери квалификации. Локальная проверка `exp`, `getClaims` и даже `getUser` не устраняют этот пробел. Пока безопасный способ подтвердить требуемую актуальность не установлен и не проверен, будущая строгая интеграция возвращает `unavailable` / `session_unverified` или `membership_unverified`. Это предлагаемый контракт следующего этапа, а не утверждение об изменении сегодняшнего runtime. Нельзя объявлять готовность к production или молча снижать требования до «подпись верна».

## Предлагаемый контракт диагностики

Сохраняются три машинных статуса. Добавление фиксированного `reason_code` — предложение для следующего PR, текущая API-схема не меняется. Отображаемая причина берётся из локального allowlist, а не из исключения SDK, HTTP body или URL. Неизвестный сбой → `unavailable` с общей безопасной причиной.

| Статус | Условие | Примеры фиксированных причин | Данные текущей попытки |
| --- | --- | --- | --- |
| `not_configured` | Источник явно не настроен/отключён | `source_not_configured` | Нет Checklist; не сетевой отказ |
| `unavailable` | Настроен, но хотя бы одно доказательство отсутствует либо запрос не завершён безопасно | `configuration_invalid`, `reauth_required`, `refresh_in_progress`, `refresh_uncertain`, `session_revoked`, `identity_unverified`, `access_expired`, `session_unverified`, `membership_unverified`, `permission_denied`, `network_timeout`, `redirect_rejected`, `transport_failed`, `stale_response_rejected`, `response_incomplete` | Пустые `items`/`reviews`, `revision` и `retrieved_at` отсутствуют; ни одного подставленного снимка |
| `verified` | Только свежий полный валидный GET текущей попытки, с подтверждённой идентичностью, живой сессией и текущими правами | `fresh_snapshot_verified` | Нормализованный снимок, revision и время получения; пункты остаются `manual_review`, пока инженерная проверка не реализована |

Например: «Требуется повторная авторизация», «Не удалось подтвердить актуальные права», «Источник недоступен: истекло время ожидания». Никаких bearer headers, паролей, JWT claims, refresh credentials, их хэшей, email или сырых сообщений Auth в UI, истории, CSV/XLSX, логах, exception chaining и CI artifacts. Историю и время попытки можно журналировать без credentials; operational correlation ID случаен и не производен от секрета. Credential API, если появится, никогда не возвращается браузеру через диагностический контракт.

Исторический успешный снимок остаётся неизменным и явно историческим. Новый отказ записывается как новый отказ, не переписывает прошлые результаты и не использует их как fallback. Проверка не перечитывает Checklist посреди расчёта: run замораживает один валидированный снимок. Существующие решения инженера и коды замечаний не связаны с обновлением авторизации.

## Протокол обновления для варианта A (проект, не реализация)

1. Проверить доверенную конфигурацию, локального principal и источник актуальных прав. Если отсутствуют — остановиться. Никакого refresh только ради обхода 403 или неизвестного членства.
2. Взять межпроцессную блокировку по ключу сессии; атомарно прочитать epoch, generation, состояние credential и pending marker из защищённого хранилища. Epoch не переиспользуется даже при перезапуске. Ожидающие запросы не делают собственный refresh.
3. Если credential утрачен/отозван/неопределён, требуется интерактивный вход. Если access ещё допустим и все права подтверждены, выполнить новый GET без refresh; не использовать его после неудавшегося refresh.
4. Перед отправкой refresh атомарно и устойчиво записать pending marker `(binding, epoch, generation, attempt)`. На аварийном старте pending → `in_doubt`; истечение lease не разрешает второму процессу переиспользовать credential. Процесс без надёжной блокировки/vault не обновляет сессию.
5. Только владелец pending отправляет один Auth refresh с ограниченным timeout. **Чтение Checklist остаётся исключительно GET. Auth refresh по протоколу использует POST к Auth, а не запись в `items`/`sections`; его внедрение требует отдельного PR. В этом PR нет даже такого POST.**
6. Проверить происхождение ответа и соответствие проекту, subject и Auth session. Атомарно сохранить согласованную ротированную пару в vault, увеличить generation и удалить pending marker. При несоответствии, ошибке записи, timeout, потере ответа или неизвестном исходе → quarantine `in_doubt`, `unavailable`, затем реавторизация. Не повторять старый refresh на основании окна reuse.
7. Повторный/запоздалый результат применяется только при совпадении pending marker, binding, epoch и generation. Logout, отзыв и новый интерактивный вход увеличивают epoch и закрывают старые попытки. Успех старого запроса не может восстановить отозванную сессию или затереть новый вход.
8. После успешного обновления заново подтвердить требуемые права и получить **новый** полный Checklist GET. Зафиксировать идентификатор попытки, epoch и generation; ответ от предыдущего пользователя, поколения или run отбрасывается. Публикация снимка и авторизационное fencing должны иметь определённую точку сериализации; уже завершённый исторический run не изменяется последующим logout.

Доказательная модель проверяет логические interleavings этих переходов, не реализует locks/CAS/vault и не доказывает отсутствие реальной гонки. В модели `COMMITTED` — внешнее предположение о проверенной идентичности и атомарной durable записи, а не просто HTTP 200. `record_verified_reauthorization` также предполагает уже завершённый доверенный вход. Реальная реализация должна доказать эти предположения отдельно.

### Хранилище и восстановление

Кандидаты для отдельного прототипа: Windows Credential Manager/DPAPI в контексте конкретного пользователя; Linux Secret Service с разблокированным пользовательским keyring. Доступность, разрешения, атомарность, поведение нескольких процессов и recovery нужно подтвердить на целевых ОС **до** выбора библиотеки/формата. Сейчас зависимости не добавляются. Plaintext, SQLite, `.env`, browser localStorage, экспортируемые файлы и общее сетевое хранилище не являются fallback для refresh credential. Заблокированный/недоступный vault → `unavailable`.

В SQLite можно сохранять только существующий снимок/статус проверки и безопасную диагностику, без credentials или их отпечатков. Сессионный координатор не следует размещать в истории проверок. Миграция этого PR не нужна. При новой авторизации и logout очистка vault и fencing должны быть согласованы; локальный logout без сети не означает гарантированный серверный отзыв, поэтому локально сразу запретить использование сессии.

OS vault не защищает от вредоносного процесса под тем же пользователем, компрометации backend или администратора. Python не гарантирует обнуление копий строк в памяти. Требуются ограниченные права процесса, исключение секретов из отладочных дампов/телеметрии и отдельный аудит; это остаточные риски, а не решённые свойства модели.

### Сеть, SSRF и повторы

- URL проекта только из доверенной настройки; точный разрешённый origin проекта, HTTPS/443, фиксированный Auth или `/rest/v1/items` path. Не принимать origin, redirect target, project ref, API key или query из PDF/браузерного ввода. Запрещены userinfo, IP/private/loopback/link-local endpoints, нестандартные схемы/порты, suffix spoofing и произвольный path. Строгая валидация конфигурации предшествует передаче заголовков.
- Редиректы запрещены и для Auth, и для GET; не пересылать Authorization/apikey на другой адрес. TLS verification включена. DNS/прокси/сетевой egress относятся к границе доверия: разрешать только ожидаемые Supabase endpoints, не использовать недоверенный proxy. Одной строковой проверки suffix недостаточно для полной защиты от DNS rebinding/компрометации сети.
- Ограничить timeout, размер и количество ответов/попыток. Сохранять текущие проверки Content-Range/полноты и запрет устаревшего снимка. Ретраи только ограниченные, явно разрешённые для свежего GET той же сессии после повторной проверки её актуальности; каждый повтор — новая попытка. 401/403, неопределённое членство и отзы́в не запускают бесконечный refresh-loop. 429/Retry-After не даёт права на неограниченный повтор или расход квот.
- Неопределённый исход refresh не повторяется автоматически. Timeout GET не становится подтверждённой проверкой благодаря предыдущему успеху. Refresh и GET не передают документы КД в Supabase или другие сервисы. Действующие проверки приложения не используют внешние AI-сервисы; этот PR ничего такого не добавляет.

## Угрозы и остаточные риски

| Угроза/отказ | Барьер и безопасный результат | Что ещё нужно доказать до внедрения |
| --- | --- | --- |
| Утечка credentials через репозиторий, историю, UI, отчёт, CI, exception | Только фиксированные причины; тесты без credentials; refresh только в OS vault; runtime сейчас не затронут | Редакция логов SDK, дампов, HTTP tracing и экспорта во всех реальных путях |
| Общая сессия двух пользователей или ПК, подмена subject | Отдельная Auth session; binding проекта/subject/session/устройства из доверенного входа | Аутентификация локального клиента, CSRF/origin и изоляция пользователей backend |
| Два одновременных refresh / несколько процессов | Single-flight, durable pending, epoch/generation/attempt fencing | Реальная блокировка Windows/Linux, crash consistency и отказ при потере lock |
| Потеря ответа ротации, crash, ошибка vault | Quarantine, никакого повторного refresh или старого access fallback; интерактивный вход | Точки отказа до/после commit и запуск после аварии |
| Запоздалый refresh после logout/смены пользователя | Старый epoch не может завершиться или опубликовать snapshot | Атомарность с logout и публикацией результата, не только refresh |
| JWT истёк/refresh потерян/сессия отозвана | `unavailable`, повторный доверенный вход; без постоянного JWT/общего секрета | Доступный способ проверки server-side revocation без новых привилегий |
| Квалификация/членство изменились при ещё валидном JWT | `membership_unverified`/`permission_denied`; fail closed | Согласованный актуальный источник полномочий; JWT metadata и 200 недостаточно |
| RLS скрыла часть строк, пустой ответ ошибочно объявлен полным | Проверки контракта и полных прав обязательны; ошибка → `unavailable` | Owner-approved доказательство права на полный набор, не только Content-Range видимых строк |
| Redirect, SSRF, подмена origin, недоверенный proxy | Точный origin, GET fixed path, запрет редиректов, проверка TLS, egress | Аудит DNS/прокси и конфигурации развёртывания |
| Нет сети, timeout, 429, некорректный JSON/Content-Range | Ограниченные попытки, безопасная причина, без stale fallback | Интеграционные fault-injection тесты без живого сервиса |
| Взлом ОС/того же пользователя | Минимальные права, vault, секреты не выводятся | Остаточный риск не устраняется этой архитектурой; требуется аудит хоста |
| Платная функция, неожиданный тариф/квота | Никаких live вызовов сейчас; будущий free-only gate, иначе выключено | Подтверждение владельцем допустимых бесплатных возможностей, не предположение о тарифе |

## Доказательная модель и регрессионный план

`design/checklist_session_model.py` использует только stdlib, неизменяемые dataclasses, фиктивные идентификаторы и счётчики. Нет credential полей, паролей, JWT fixtures, SDK, запросов, файлового/DB доступа или чтения окружения. Состояния `absent`, `ready`, `in_doubt`, `revoked` относятся к абстрактному координатору; внешние статусы проверки остаются прежними. Старый снимок не является входом функции решения.

`tests/test_checklist_session_design.py` проверяет:

- отсутствие конфигурации, отсутствие каждого обязательного доказательства и все 64 комбинации признаков авторизации/полноты;
- свежий успешный ответ и отказ сети/timeout/redirect/403 после предыдущего успеха без изменения исторического решения;
- другой проект, пользователь, Auth session и ПК; устаревшие request ID, epoch и generation;
- один победитель refresh, отказ второго, дубликаты и поздние завершения, GET до ротации;
- неопределённый исход refresh, запрет повторного использования, необходимость нового интерактивного входа;
- отзыв, logout/смену пользователя/новый вход во время refresh и независимость двух ПК;
- только фиксированные безопасные причины, без отражения произвольного текста ошибки.

Запуск на Windows и Linux: `python -m pytest -q tests/test_checklist_session_design.py`, затем `python -m pytest -q`. Существующий CI запускает весь набор на Python 3.13, `ubuntu-latest` и `windows-latest`, включая Playwright UI. Никаких новых зависимостей или внешних запросов из тестов модели. Установка существующих зависимостей/Chromium в CI отличается от сетевых вызовов тестируемого приложения; реальные Supabase endpoints не вызываются.

Следующий PR должен добавить автономные adapter-тесты с фальшивыми транспортом, vault, часами и источником полномочий: все точки crash до/после pending и commit, реальные многопроцессные гонки, expiry/clock skew, утрата прав при refresh и GET, 401/403/429/5xx, таймауты на разных стадиях, недопустимые URL и редиректы обоих endpoints, Content-Range и неполные sections, vault locked/denied, отсутствие утечки во всех API/CSV/XLSX/log путях. Проверить историческую повторяемость, ручные решения инженера и отсутствие cache fallback. Если будет UI входа — отдельные synthetic browser-тесты CSRF/origin/PKCE/callback и одновременных пользователей. Это **план**, а не пройденные тесты реального Auth/vault/production.

## Условия следующего этапа и откат

До runtime-реализации review должен подтвердить вариант A/B/C, доверенный способ входа и принадлежности пользователя, источник актуальной квалификации и отзыва, безопасность vault/координатора на обеих ОС, бесплатность и допустимость запросов, модель угроз локального UI. Если хотя бы один пункт не подтверждён, автоматическое обновление не внедряется. Смена политики RLS или добавление полномочий не являются способом снять блокировку в рамках этой задачи.

После решения — отдельный PR с реализацией и аудитом, выключенный по умолчанию, затем синтетические интеграционные проверки и только отдельно согласованный пилот. Никаких автоматических merge/deploy. Этот PR можно откатить удалением новых `design/`, теста и документа; база, история, сессии и действующий Checklist не требуют восстановления, так как не изменялись.
