# Синтетическая приёмка двух независимых экземпляров защищённого HTTP

Это **не испытание двух физических компьютеров**: одновременно запускаются два независимых `create_secure_app` в тестовых ASGI-клиентах на одной машине. Они используют отдельные объекты `ScopedBackend` и `DurableSessions`, но общие временные локальные SQLite-файлы. Реальные документы предприятия, сетевые подключения, TLS-прокси, production SSO и Supabase не используются.

## Проверяемые свойства

1. Два конкурирующих `PATCH /api/runs/{run_id}/findings/{finding_id}` с одинаковой `expected_version=0`: ровно один HTTP 200 и один HTTP 409, без двойных событий аудита; оба экземпляра видят одну версию и одни данные.
2. Два конкурирующих `PUT /api/config` с одинаковой исходной версией: одна успешная запись и один конфликт; оба экземпляра видят ровно одну цепочку конфигурации и версию 1.
3. Один экземпляр завершает сессию `/auth/logout`, второй немедленно отказывает по тому же старому cookie (401), не только после перезапуска.
4. Смена полномочий engineer→viewer в общей базе после входа запрещает запись в обоих экземплярах и не создаёт событие аудита, сохраняя разрешённое чтение.
5. CSRF-токен сессии другого клиента нельзя использовать для создания проверок; база не получает частичного run.

Сценарии запускаются на **синтетическом PDF** и двух независимых HTTP-клиентах, проходят через настоящие middleware, роли и SQLite. Оба клиента не переподключаются к одному общему объекту backend; для истории и сессий используются независимые экземпляры репозиториев. Тестовая идентификация выполняется только через жёстко заданный verifier.

## Ограничения

Не подтверждены: два Windows-ПК, транспорт LAN, production TLS/SSO, поведение общей SQLite на сетевом диске (это запрещённая архитектура), PostgreSQL, distributed lock, общий лимит workers и отказ сети. Результаты подтверждают только транзакционную и HTTP-согласованность для локальной тестовой SQLite.

Ни runtime, ни интерфейс Codex не изменяются. Ветка зависит от #69/#68/#65 и предыдущих PR. Для тестов используется временная цель `main`, так как действующий GitHub workflow запускается только для PR в `main`; при этом diff включает неслитые родительские коммиты. Не объединять до родителей и ручного review.

Команда: `python -m pytest -q tests/test_two_instance_http_consistency.py`, затем единый полный CI Windows/Linux без повторных запусков без причины. Аккаунт GitHub Billing и платные ресурсы не изменяются.
