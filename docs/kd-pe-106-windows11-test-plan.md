# KD-PE-106: план приёмки на Windows 11 и на реальных Э3/ПЭ3

Статус: **NOT VERIFIED**. Ни одна проверка этого документа не выполнялась:
среда SourceCraft — Linux-контейнер без Windows 11 и без реальных комплектов.
Документ описывает воспроизводимую процедуру, которую выполняет инженер.

## 1. Границы

- Отдельная папка: `C:\KD-Checker-acceptance`.
- Не изменяются `C:\KD-Checker\work`, `C:\KD-Checker\codex`,
  `C:\KD-Checker\integration`, `C:\KD-Checker\coordination`.
- Реальные PDF/XLSX не копируются в репозиторий и не публикуются.
- Merge, push, изменение Supabase и EPLAN Checklist не выполняются.
- Платные сервисы, облачный ИИ и внешние API не используются.

## 3. Автоматизированный прогон

```powershell
# из любой папки, кроме рабочих каталогов KD-Checker
powershell -ExecutionPolicy Bypass -File tools\windows11_acceptance.ps1 `
    -ExpectedSha 1d1b603cae14f2adba8c043e85404e239aae4d96 `
    -WorkDir C:\KD-Checker-acceptance `
    -PythonCommand "py -3.13"
```

Скрипт выполняет по порядку:

| № | Шаг | Что доказывает |
|---|---|---|
| 1 | `git clone` + `git fetch` | развёртывание из GitHub |
| 2 | `git cat-file` + `git checkout --detach` + `git rev-parse HEAD` | точный SHA, а не «похожая» ветка |
| 3 | `python -m venv .venv`, `pip install -r requirements*.txt` | изолированное окружение |
| 4 | `python tools\dependency_policy.py` | политика зависимостей |
| 5 | целевые тесты KD-PE-105 | 162 ожидаемых теста |
| 6 | `python -m pytest -q` | полный набор (ожидается 1099 passed, 1 skipped) |
| 7 | `python acceptance_stand.py --json acceptance-report.json` | инженерные сценарии A–H |
| 8 | `python synthetic_stand.py accept --synthetic-only --workspace .\acceptance-stand` | синтетическая приёмка приложения |
| 9 | `start_windows.bat` + `http://127.0.0.1:8765` | запуск и доступность интерфейса |
| 10 | повторный запуск | воспроизводимость запуска |

Журналы: `C:\KD-Checker-acceptance\logs\*.log`.
Машинная сводка: `C:\KD-Checker-acceptance\windows11-acceptance-summary.json`.
Код выхода: `0` только при полном успехе; `1` при любом FAIL или NOT_VERIFIED.

## 4. Ручные контрольные точки

После автоматического прогона инженер проверяет в интерфейсе:

1. Загрузка синтетических PDF и появление результата.
2. Отображение кода `KD-PE-105`, уровня и достоверности.
3. Документ, лист Э3 и лист/строку ПЭ3 в карточке замечания.
4. Отсутствие вымышленной строки, если сетка PDF не подтверждена.
5. Список отсутствующих обозначений и контекст.
6. Выгрузка CSV: строго 6 колонок, без изменения схемы.
7. Выгрузка XLSX: лист «Замечания», колонки K/L при наличии `details`.
8. Повторная проверка: решения инженера не переносятся автоматически.
9. История: сохранение результата после перезапуска приложения.
10. Корректное завершение: закрытие консоли, отсутствие зависших процессов.

Каждая точка фиксируется в протоколе: шаг, ожидание, факт, вердикт.

## 5. Критерии приёмки Windows 11

| Критерий | Условие PASS |
|---|---|
| SHA | `git rev-parse HEAD` равен ожидаемому |
| Тесты | 0 failed; каждый skipped объяснён |
| Стенд A–H | все 8 сценариев PASS, exit code 0 |
| Приложение | интерфейс открывается, проверка выполняется, отчёт выгружается |
| Повторный запуск | успешен, история сохранена |
| Журналы | сохранены и приложены к протоколу |

Расхождение числа тестов с Linux-прогоном допустимо только при объяснении
каждого отличия. Необъяснённое расхождение — FAIL приёмки.

## 6. Ограничения автоматизации

- Скрипт не заменяет инженерную проверку содержания документов.
- Проверка UI ограничена фактом загрузки страницы и наличием заголовка.
- Скрипт не проверяет визуальную вёрстку на разных разрешениях.
- Скрипт не выполняет merge и не публикует результаты.

## 7. Приёмка на реальных Э3/ПЭ3

### 7.1 Что необходимо предоставить

| Тип комплекта | Назначение |
|---|---|
| Корректный комплект Э3 + ПЭ3 | проверка отсутствия ложных замечаний |
| Комплект с известным дефектом (обозначение есть в Э3, отсутствует в ПЭ3) | проверка обнаружения |
| Комплект с неполной записью ПЭ3 (количество больше раскрытых обозначений) | проверка доказательства |
| Многолистовой комплект | проверка сохранения листа происхождения |
| PDF без текстового слоя | проверка явного ограничения проверки |

Документы остаются на машине инженера; в репозиторий попадают только
обезличенные результаты.

### 7.2 Порядок

1. Запустить приложение на Windows 11 по разделу 3.
2. Загрузить комплект, выполнить проверку, сохранить CSV и XLSX.
3. Для каждого замечания `KD-PE-105` сверить вручную:
   обозначение, лист Э3, лист и строку ПЭ3, количество, число обозначений.
4. Отдельно проверить отсутствие замечаний там, где их быть не должно.
5. Заполнить таблицу «ожидаемое / фактическое» и реестр дефектов.
6. Повторить прогон после исправления документов.

### 7.3 Таблица ожидаемых и фактических результатов

| ID | Комплект | Проверяемое правило | Ожидаемый результат | Фактический результат | Вердикт | Доказательство |
|---|---|---|---|---|---|---|
| R-01 | корректный | нет ложных KD-PE-105 | 0 замечаний | | | CSV/XLSX |
| R-02 | известный дефект | отсутствие в ПЭ3 | warning с обозначением | | | лист/строка |
| R-03 | неполная ПЭ3 | количество > обозначений | warning с доказательством | | | количество |
| R-04 | многолистовой | лист происхождения | указан верный лист | | | e3_pages |
| R-05 | без текста | ограничение проверки | явное замечание, не успех | | | сообщение |
| R-06 | дубли ПЭ3 | `KD-PE-104` | warning при подтверждённой сетке | | | лист/строка |

### 7.5 Что считается доказательством

- Для пропуска несоответствия: конкретное обозначение, присутствующее в Э3,
  отсутствующее в ПЭ3, при подтверждённой строке ПЭ3.
- Для ложного срабатывания: обозначение, которое не является изделием
  (контакт, ссылка, примечание), либо строка ПЭ3, покрывающая обозначение.
- Скриншот интерфейса без координат и содержимого документов.
