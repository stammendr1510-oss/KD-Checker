# KD-PE-106: независимая инженерная приёмка KD Checker

Дата: 22.11.2026. Статус продукта: **ACCEPTANCE PENDING**.
Статус работ SourceCraft: проверки выполнены, стенд создан, дефекты
зарегистрированы, приёмка на Windows 11 и на реальных Э3/ПЭ3 **не выполнена**.

## 1. Главный вопрос

Можно ли текущей версией KD Checker самостоятельно выполнять предварительную
проверку реальных Э3 и ПЭ3 перед выпуском КД — так, чтобы инженер мог доверять
и найденным несоответствиям, и отсутствию замечаний.

Ответ на уровне выполненных проверок: **частично**. Текстовое сопоставление
обозначений Э3 и строк ПЭ3 воспроизводимо и осторожно, но:

- Windows 11 не проверялся;
- реальные Э3/ПЭ3 не проверялись;
- часть семейств обозначений вообще не анализируется (см. ограничения);
- правило «примечание/таблица в строке» может скрыть реальное несоответствие.

## 5. Независимые инженерные испытания A–H

Все документы синтетические и создаются в памяти (PyMuPDF). Реальные PDF/XLSX
не использовались и не добавлялись.

| Сценарий | Вход | Ожидание | Факт | Машинный критерий | Тест |
|---|---|---|---|---|---|
| A. Корректный комплект | Э3: QF1, QF2, KM1, TA1, SB1; ПЭ3: те же позиции | нет ложных warning | warning KD-PE-105 = 0 | `len(warnings)==0` | `scenario_a` |
| B. Нет в ПЭ3 | Э3: QF1..QF3; ПЭ3: QF1, QF2, количество 3 | warning с доказательством | warning=1, `missing=['1QF3']`, `confidence=high`, `valid=True` | warning=1, missing, `valid_details` | `scenario_b` |
| C. Лишняя позиция ПЭ3 | ПЭ3 содержит QF9 без Э3 | не ошибка, только info | KD-PE-105 = 0, KD-PE-101 = info | нет KD-PE-105 | `scenario_c` |
| D. Дубли и многолистовые ссылки | QF1 на листах 1 и 2 | нет ложного отсутствия | KD-PE-105 = 0 | нет KD-PE-105 | `scenario_d` |
| E. Неоднозначные обозначения | X1, XT1, SF1, QF1, KM1, SB1, K1, KA1, HL1, X1:2 | X1 ambiguous, XT/SF/QF/KM/SB изделия, X1:2 вывод | совпало | категория каждого токена | `scenario_e` |
| F. Форматы | регистр, кириллица, дефис, пробел, индекс, контакт | нет «исправления» обозначений | `1-KM1` ambiguous, `XT4.2` вывод, остальное как ожидалось | категория каждого формата | `scenario_f` |
| G. Повреждённые документы | пустой PDF, битый PDF, битый XLSX, PDF без текста, нет пары | нет ложного успеха | отклонение при чтении, `KD-PE-000`, `KD-SET-101` | blocking code / rejection | `scenario_g` |
| H. Многолистовая схема | QF1 лист 1, QF2 и ссылка на QF1 лист 2 | missing только QF2, лист 2 сохранён | `missing=['1QF2']`, `e3_pages=[2]` | missing + e3_pages | `scenario_h` |

Инженерные обоснования:

- A: совпадение обозначений не должно создавать работу инженеру.
- B: количество 9 при 7 раскрытых обозначениях — доказательство неполной записи,
  а не источник выдуманных позиций.
- C: ПЭ3 может содержать позиции, не отображаемые на данной схеме; правило
  проверяет только направление «есть в Э3, нет в ПЭ3».
- D: многолистовые ссылки — норма, а не дубль.
- E: вывод устройства не является изделием; одиночное `X1` неоднозначно.
- F: неоднозначное обозначение нельзя «починить» молча.
- G: нечитаемый документ обязан давать явное ограничение проверки.
- H: потеря листа происхождения делает замечание непригодным для инженера.

Ни один P0 не подтверждён. Исправлен один P2 (KD106-01). Два открытых пункта
(P1 KD106-03, P2 KD106-02) требуют инженерного решения, а не «зелёного теста».

### Варианты решения по KD106-03

1. Расширить `TAG_PREFIX` семействами `K`, `KA`, `HL` и добавить регрессии для
   KD-PE-100…104. Риск: новые ложные срабатывания на тексте, похожем на
   обозначения.
2. Ввести отдельный конфигурируемый список семейств только для KD-PE-105.
   Риск: расхождение правил между проверками.
3. Оставить как ограничение и требовать от инженера ручной проверки этих
   семейств. Риск: систематический пропуск.

### Варианты решения по KD106-02

1. Считать маркер ссылкой только при расположении перед обозначением
   (`см. QF1`) либо при явной ссылке на лист/документ.
2. Учитывать только те маркеры, которые не являются заголовками столбцов
   (`примечание`, `наименование`, `количество`).
3. Оставить консервативно и явно показывать инженеру, что строка не проверялась.

- не изменяет production и не пишет в рабочую историю.
