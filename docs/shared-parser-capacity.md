# Общая квота parser-worker изолированного стенда

Зависимость: #85 и его родители. Каждый `ScopedBackend` при доверенном startup
создаёт пустой gate-файл рядом с каноническим путём scoped SQLite:
`history.sqlite3.parser-capacity`. Все экземпляры, использующие **тот же локальный
файл репозитория**, используют одну квоту: не более одного одновременно работающего
парсера. Не переносить gate или SQLite на сетевой диск.

Lock захватывает **сам worker**, до импорта движка и чтения документов в parser.
POSIX использует неблокирующий `flock`, Windows — `msvcrt.locking` первого байта
(диапазон может находиться за концом пустого файла). Занятость даёт безопасный HTTP
503 без сохранения run; ожидания свободной квоты и очереди нет. Parent сохраняет
свой прежний semaphore и жёсткий timeout. Это не квота разных репозиториев, серверов
или контейнеров и не защита от произвольного кода, игнорирующего advisory lock.

Worker владеет lock до завершения обработки. При kill/обычном выходе ОС освобождает
его автоматически. Gate никогда не удаляется и не заменяется: удаление создало бы
новый независимо блокируемый inode. Не нужны lease, TTL или ручное удаление
«устаревших» lock-файлов. Не удалять gate во время работы сервера. При аварии parent
на POSIX orphan-worker может продолжать работать и удерживать квоту; это намеренный
безопасный отказ, а не допуск второго parser. Существующие CPU limits сохраняются,
но sleeping orphan требует штатного завершения процесса оператором/supervisor.
Windows kill-on-close Job Object предназначен для завершения worker при смерти
parent, однако это ещё требует фактической Windows-приёмки.

Только startup создаёт gate, только в доверенном каталоге. Child открывает уже
существующий файл и не создаёт отсутствующий. При неизвестной ОС, неправильном типе
файла, непустом содержимом, symlink/hardlink или смене inode операция отказывает.
На POSIX также проверяются owner и private mode. На Windows 0600 не заменяет ACL:
каталог и файлы должны быть закрыты для посторонних; ACL ещё не испытаны. Локальный
пользователь с правом замены файлов может нарушить квоту. Это не OS sandbox.

Небольшой bootstrap запускается и временные входные файлы создаются **до** захвата
lock worker-ом. Они ограничены существующими лимитами входа, но общая квота
multipart/spool/памяти нескольких HTTP-процессов не реализована этим блоком. Стенд
по-прежнему запускает один HTTP worker. `run_check` как внутренний низкоуровневый
helper сохраняет необязательный capacity для preflight; защищённый backend всегда
передаёт свой gate. HTTP не может выбрать путь gate или отключить квоту.

Gate не содержит данных и не входит в backup: восстановленный репозиторий получает
свой gate при startup. Две независимые копии хранилища имеют отдельные квоты.
Снимки происхождения запуска не меняют формат v1; версия политики квоты отражается
в source fingerprint, а не в пользовательских настройках.

Синтетические проверки: отдельный процесс держит lock и принудительно завершается;
реальные два HTTP backend получают 503 при занятости и сохраняют run после
освобождения; timeout убивает lock-owner до повторного запуска; missing gate,
symlink/hardlink, непустой файл и POSIX permissions отказывают без перезаписи.
Локальные Linux результаты не подтверждают Windows и совместную работу двух ПК.
