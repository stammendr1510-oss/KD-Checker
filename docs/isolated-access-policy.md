# Изолированный прототип политики доступа

Статус: **не подключён к runtime**. Этот PR добавляет только чистую функцию принятия решения `design/access_policy.py` и синтетические тесты. Текущие API FastAPI остаются без аутентификации; открывать локальный MVP для других ПК **нельзя**.

## Контракт

`is_allowed(principal, action, resource)` разрешает действие только при верифицированной сессии, явно известной роли и совпадающей идентичности организации у субъекта и ресурса. Отсутствующий principal, объект, неизвестная роль, действие или чужая организация запрещаются. Набор прав:

| Роль | Читать | Начать проверку | Изменить решение | Настроить правила |
| --- | --- | --- | --- | --- |
| viewer | да | нет | нет | нет |
| engineer | да | да | да | нет |
| admin | да | да | да | да |

Это проектная матрица, требующая согласования владельца перед внедрением.

## Критические предпосылки будущей интеграции

- `Principal` создаётся **только** доверенным серверным компонентом после проверки действительности сессии, идентичности и членства. Значения `subject`, `role`, `organization_id` и `session_verified` из тела HTTP, cookie без верификации или заголовка пользователя не являются подтверждением.
- `Resource.organization_id` извлекается **только** из централизованной БД по идентификатору объекта с проверкой допустимости доступа. Имя файла, query parameter или `run_id` не доказывают принадлежность.
- Для сравнения двух проверок права проверяются на **обе**; для статуса замечания — на run и finding, для выгрузки — на тот же объект, что и при чтении.
- Политика не выполняет logout, refresh, CSRF, rate limit, аудит, отзыв сессии и не защищает от обмана при создании Principal. Эти функции должны быть реализованы и протестированы отдельно до подключения общего доступа.
- PR #23 решает отдельную задачу чтения EPLAN Checklist. Его токены и RLS не становятся автоматически системой ролей KD Checker.
- Никакого изменения работающих Supabase, EPLAN Checklist, SQLite, запуска FastAPI или внешних платных сервисов.

## Необходимые следующие независимые шаги

1. Согласовать модель пользователей и организаций, затем определить доверенный источник сессий и текущего членства.
2. Добавить серверный authentication boundary с явным отказом (401) для гостя и отсутствующей/отозванной сессии.
3. Для каждого API route добавить привязку действующего principal к проверенному объекту, возвращая 403/404 для чужого ресурса без раскрытия данных.
4. Добавить интеграционные тесты 401/403/IDOR/CSRF и только после этого рассматривать HTTPS/LAN развёртывание.

Тесты данного PR доказывают лишь логику изолированной функции. Они **не** являются подтверждением выполнения G1–G7 многопользовательской приёмки.
