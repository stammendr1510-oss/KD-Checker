## Целевой сервер и режим совместимости

Браузеры → HTTPS reverse proxy → отдельная фабрика центрального FastAPI →
серверный репозиторий данных → централизованная транзакционная СУБД.
Парсеры документов запускаются ограниченными заданиями вне процесса HTTP.
Локальная фабрика остаётся на loopback с прежним SQLite и форматом истории.
Центральный режим включается только явной конфигурацией; при отсутствии
identity provider, secret store, tenant repository или TLS-настроек не стартует.
Ошибки центральной конфигурации не переводят сервер в незащищённый local mode.

Источник пользователей предприятия неизвестен. Будущий изолированный прототип
получает интерфейсы IdentityVerifier и MembershipRepository с синтетическими
реализациями только в тестах. Тестовый логин и доверие заголовкам не допускаются
в production. Нельзя использовать текущий JWT Checklist как общую сессию.

## Сессия, роли и объектный доступ

- Серверная непрозрачная случайная session cookie, в БД только её хеш; Secure,
  HttpOnly, SameSite, ограниченный path, без токенов в URL/localStorage/отчётах.
- Сервер проверяет revoked_at, абсолютное и idle expiry, пользователя и текущее
  членство на каждом запросе. Неизвестное состояние запрещает доступ.
- Logout отзывает запись до успешного ответа и очищает cookie. Переавторизация
  меняет идентификатор сессии; истечение/смена роли не сохраняют старые права.
- viewer читает разрешённые данные; engineer также проверяет и принимает решения;
  admin управляет настройками **в своей области**, без глобального tenant bypass.
- Членство задаётся (user, organization, project, role). Идентификаторы области
  извлекаются из серверных записей, не тела/имён документов. Одного совпадения org
  из PR 44 недостаточно. Отзыв project grant проверяется также у administrator.
- Каждый запрос репозитория включает org/project. Список фильтруется в БД,
  запрещена загрузка всех записей с последующей клиентской фильтрацией.
- Для compare проверяются оба run; для finding — связь finding→run→project;
  CSV/XLSX/history получают ровно те же проверки, что чтение run.

Гость — 401, нехватка роли — 403, чужой/отсутствующий объект — одинаковый 404
без метаданных. Запись: synchronizer CSRF token, привязанный к сессии, сравнение
без утечки по времени, exact Origin allowlist; отсутствие необходимых доказательств
запрещает изменение. SameSite и CORS не заменяют CSRF. Методы вне allowlist
отклоняются; GET/HEAD не меняют решения. TrustedHost и trusted proxy задаются
явно; пользовательский forwarded identity не принимается. OpenAPI/docs/static
имеют явную политику и не обходят API gate. Отсутствие классификации маршрута
запрещает доступ, включая будущие маршруты.

## Модель центрального хранения — логическая, без SQL-миграции

| Сущность | Обязательные данные и инварианты |
| --- | --- |
| organizations/projects/memberships | Уникальные ID, project принадлежит org; активное членство user/org/project/role |
| runs | org/project/run UUID, created_at UTC, actor, версия алгоритмов/настроек, неизменяемые имена и результаты |
| findings | ID, run, ordinal, fingerprint версии v1, source/location/evidence; без смешения с решением |
| decisions | finding, org/project, status/comment/version, actor и дата; compare-and-set ожидаемой версии |
| decision_events | append-only старое/новое значение и версии, actor из сессии, request ID; событие и изменение в одной транзакции |
| run_links | Оба run в одном org/project, предыдущий раньше; неоднозначность не угадывается, статус не переносится |
| sessions | hash ID, user, expiry/revocation; секреты не хранятся в audit |
| migrations/import_batches | Версия схемы, digest источника, отображение legacy ID→UUID, статус и контрольные суммы |

Составные ограничения должны исключать cross-project связи даже при ошибке
приложения. Полномочия проверяются внутри транзакции изменения; повтор одного
expected_version не перезаписывает решение. Событие аудита не должно фиксироваться
без успешного изменения, или наоборот. Приложению запрещено редактировать audit
задним числом. Технический журнал использует фиксированные reason codes, без
credentials, исходных документов, cookie, сырых HTTP bodies и произвольных исключений.

Выбор движка, размещения и retention пока не утверждён. PostgreSQL допустим как
кандидат на существующем ресурсе предприятия, без создания платной инфраструктуры.
До выбора движка не добавлять фиктивный production SQL. Рабочий Supabase не цель
миграции. Общий SQLite на сетевой папке запрещён.

## Миграционный путь и восстановление

1. Остановить local writer, получить проверенную копию в новый файл (PR 45).
2. Проверить схему, FK, JSON записей и ограничения размеров; неизвестное отклонять.
3. Назначить org/project через явный подписанный оператором import manifest:
   legacy история не содержит этих данных, выводить их из имён недопустимо.
4. Импорт в пустую staging БД одной версией мигратора, транзакции по batch,
   уникальный source digest; повторный импорт того же batch не создаёт дубликаты.
5. Сохранить исходные timestamps, issues, решения, версии и порядок событий,
   предыдущие ссылки. Старые события без actor помечать legacy_unknown,
   не приписывать текущему оператору. Проверить counts/digests/FK и отчёты.
6. Провести restore центральной БД в отдельный стенд и отрицательные tenant-тесты.
7. Только после отдельного разрешения cutover, без двойной записи local/central.
   Откат до новых записей — возврат неизменённой local копии; после новых записей
   нужен согласованный обратный экспорт, иначе потеряются решения инженеров.

PR 45 не реализует шаги 2–7 целиком и не меняет production. Требуются отдельные
тесты прерванного импорта, повторного запуска, поломки связей и отказа audit write.

## A–G и расширение правил

План A–G и каталог существующих кодов уже подготовлены в PR 46. Повторно их
не создавать. A/B/D/F/G имеют рабочие ограниченные эвристики, указанные в README;
C получает opt-in ядро PR 47. Ни одна из этих частей не доказывает ГОСТ.

Для E следующий прототип: RuleDefinition(rule_id, standard_id, edition, clause,
applicability, required_evidence, evaluator_version). Если нет проверенного текста
нормы, редакции, применимости и достоверных полей документа, evaluator возвращает
not_evaluated с причиной, а не pass/ошибку КД. После экспертного review разрешается
конкретный deterministic evaluator с положительными/отрицательными fixtures.
Нормативные номера и параметры предприятия в этом запуске не выдумываются.

Для G следующий прототип сравнивает только явно извлечённые атрибуты одного
проверенного project/document/revision; конфликт редакций запрещает автоматический
выбор. Для F листность остаётся design-only до подтверждённых рамок/экспорта.
