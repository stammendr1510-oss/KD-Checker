# KD Checker — контрольные условия перехода к общей системе нескольких ПК

Статус: проект архитектурных условий, **не реализация**. Исходная база: `main` на 15.11.2026. Не изменяет работающие сервисы, права или БД.

## Целевая схема

Браузеры инженеров на отдельных ПК → HTTPS reverse proxy → централизованный FastAPI → централизованная БД проверок и решений → резервное копирование.

Это **целевая схема**, а не описание текущего развёртывания. Нынешний MVP использует loopback и SQLite без ролей. Открывать его порт в LAN до выполнения условий ниже запрещено.

## Контрольные условия (gates)

| Gate | Проверяемое требование | Минимальное доказательство | Статус |
| --- | --- | --- | --- |
| G1 | Индивидуальная аутентификация; серверная проверка каждой сессии; logout и истечение сессии запрещают новые операции | Тесты 401/403, logout, expiry, повторного входа, изоляции cookie и CSRF | не выполнено |
| G2 | Роли: администратор, инженер, просмотр; серверная проверка прав на каждый endpoint и объект | Матрица разрешений и отрицательные API-тесты, включая IDOR | не выполнено |
| G3 | Изоляция организации/проекта и запрет доступа к чужим проверкам, файлам и комментариям | Два независимых пользователя/проекта, cross-tenant тесты на чтение/изменение/экспорт | не выполнено |
| G4 | Транзакционная централизованная история и одновременная работа | Тесты конкурентного редактирования, миграции, rollback и сохранения журнала | не выполнено |
| G5 | TLS, безопасные cookies, CSRF, trusted hosts, ограничение запросов и изоляция обработки недоверенных PDF | Конфигурационный аудит и интеграционные security-тесты | не выполнено |
| G6 | Восстановление после сбоя и управляемые обновления | Практический restore из резервной копии, миграция и rollback на стенде | не выполнено |
| G7 | Реальные приёмочные испытания с двух отдельных Windows ПК | Протокол двух инженеров: одновременные проверки, права, отчёты, отключение сети, восстановление | не выполнено |

Статусы выше означают **отсутствие подтверждения в рамках данного этапа**, а не доказательство отсутствия любых частичных разработок. Выполнение каждого gate подтверждается отдельным PR, успешным CI и протоколом приёмки.

## Разграничение EPLAN Checklist и KD Checker

PR #23 касается пользовательского чтения EPLAN Checklist через Supabase и остаётся design-only. Его нельзя считать реализацией входа в KD Checker или основанием для открытия локального FastAPI другим ПК. Нельзя переносить JWT, refresh credentials или service-role ключи между инженерами и ПК; не допускается глобальная общая сессия. Ошибка доступа к Checklist должна оставаться отказом без использования устаревшего снимка. Не изменять RLS, Supabase, EPLAN Checklist или работающий сайт в рамках этого документа.

## План независимых PR

1. `auth-contract`: инвентаризация API-маршрутов и матрица прав; синтетические тесты отказа по умолчанию, без включения сетевого доступа.
2. `auth-local-prototype`: изолированный прототип индивидуальной аутентификации и серверных сессий; отдельно определить доверенный источник пользователей, CSRF и безопасный logout. Не принимать общий refresh credential.
3. `central-storage`: схема централизованной БД, миграция SQLite, конкурентные изменения и журнал; резервное копирование и восстановление.
4. `deployment-security`: HTTPS, proxy, лимиты, аудит, управление секретами, тесты изоляции.
5. `two-pc-acceptance`: испытания на двух Windows ПК и решение о пилотном запуске.

## Правило выпуска

Ни один из G1–G7 нельзя отмечать готовым только по README, design PR или зелёному CI. До подтверждения всех gates приложение остаётся локальным MVP. Любое изменение безопасности должно быть обратно совместимым с локальным режимом либо иметь явно документированную миграцию и откат. Реальные КД и действующие учётные данные в тестах не используются.
