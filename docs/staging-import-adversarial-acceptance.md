# Независимая отрицательная приёмка staging-импорта истории

Тесты построены поверх PR #56 и его зависимостей (#45, #55). Работают только с искусственной локальной SQLite, новой резервной копией и новым staging-файлом. Реальные документы, пользователи предприятия, Supabase и EPLAN Checklist не используются.

## Сценарии

- Испорченный JSON сохранённых файлов и замечаний, пропущенное состояние замечания, нарушенная версия или статус аудита, отсутствующий scope запуска должны блокировать импорт без создания staging.
- Неуказанные оператор и редакция либо чрезмерно длинные значения отклоняются **до создания** резервной копии.
- Уже существующая копия или staging никогда не заменяются, исходная база не изменяется.
- `import_manifest.source_sha256` совпадает с SHA-256 проверенной SQLite-копии.
- Необязательные `checklist_run_snapshots` сохраняются только в архиве исходных данных, без включения live Checklist-интеграции.
- Исходные события имеют автора `legacy_unknown`, новые решения после импорта — явного оператора; цепочка версий сохраняется и продолжается.
- После переноса выполняются `integrity_check` и `foreign_key_check`.

## Ограничения

Импорт требует **доверенного оператора** и остановленной исходной базы. Назначение всей истории одной организации/проекту и редакции — явное решение; автоматическое угадывание идентичности по именам не допускается.

Тесты не удостоверяют подлинность legacy-истории, не проверяют многокомпьютерный PostgreSQL, не выполняют production cutover, не заменяют процедуру backup/restore предприятия и не активируют native EPLAN.

## Запуск

`python -m pytest -q tests/test_staging_import_adversarial_integrity.py`

После целевых тестов — полный CI Windows/Linux один раз по завершённому PR. Базовая ветка PR для запуска существующего workflow — `main`, но diff включает неслитые родительские изменения. Принимать только после #56 и его зависимостей; автоматическое слияние запрещено.

## Бюджет

Ручные повторные прогоны не запускаются при успешном CI. Оставшийся включённый лимит GitHub Actions нельзя вычислить из PR; его нужно сверять с разделом Billing.
