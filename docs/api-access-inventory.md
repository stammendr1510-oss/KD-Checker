# Инвентаризация доступа к API — проект ролей (без реализации)

Дата: 15.11.2026. Источник: маршруты `app.py` в `main` на момент подготовки PR. Сопровождающий тест: `tests/test_api_access_inventory.py`.

**Текущий факт:** FastAPI MVP слушает `127.0.0.1:8765` без встроенной аутентификации и серверной проверки ролей. Приведённые ниже роли — **проектная политика**, а не действующая защита. Прохождение теста означает только полноту инвентаризации маршрутов. До реализации G1–G7 запрещено открывать текущий MVP в LAN.

| Метод | Путь | Предлагаемая минимальная роль | Проверка объекта перед доступом |
| --- | --- | --- | --- |
| GET | `/api/config` | viewer | область проекта/организации |
| PUT | `/api/config` | admin | право настройки проекта; CSRF |
| POST | `/api/check` | engineer | право создать run в проекте; лимиты и CSRF |
| GET | `/api/runs` | viewer | только разрешённые runs, серверная фильтрация |
| GET | `/api/runs/{run_id}` | viewer | владелец/участник проекта run |
| GET | `/api/runs/{run_id}/compare/{previous_run_id}` | viewer | доступ к **обоим** runs и их совместимость |
| GET | `/api/runs/{run_id}/checklist-compare/{previous_run_id}` | viewer | доступ к обоим runs и Checklist |
| GET | `/api/runs/{run_id}/checklist-compare/{previous_run_id}/csv` | viewer | доступ к обоим runs; безопасная выгрузка |
| GET | `/api/runs/{run_id}/checklist-compare/{previous_run_id}/xlsx` | viewer | доступ к обоим runs; безопасная выгрузка |
| GET | `/api/runs/{run_id}/csv` | viewer | доступ к run и экспорту |
| PATCH | `/api/runs/{run_id}/findings/{finding_id}` | engineer | доступ к run и конкретному замечанию; CSRF/конфликты |
| GET | `/api/runs/{run_id}/findings/{finding_id}/history` | viewer | доступ к run и замечанию; журнал может раскрывать данные |
| GET | `/api/runs/{run_id}/xlsx` | viewer | доступ к run и экспорту |

Дополнительные поверхности: `/` и `/static` пока отдают интерфейс без аутентификации, `/docs`, `/redoc`, `/openapi.json` FastAPI создаёт автоматически по умолчанию. Их политика (закрыть, ограничить или показывать минимум без данных) требует отдельного решения. Контроль HTTP методов, HEAD/OPTIONS и CORS также обязателен.

## Обязательные отрицательные тесты в последующем auth PR

1. Гость получает 401 на чтение, запись, историю, сравнение и все экспорты; не возвращаются данные из SQLite.
2. Viewer получает 403 для POST проверки, PUT настроек и PATCH замечания.
3. Engineer получает 403 для PUT настроек; может менять только разрешённые замечания.
4. Пользователь проекта A получает 404 или 403 (без раскрытия метаданных) при доступе к run проекта B, включая CSV/XLSX и оба аргумента сравнения.
5. Истёкшая, отозванная или чужая сессия не даёт доступ; CSRF и чужой Origin не изменяют состояние.
6. Параллельные PATCH одного замечания сохраняют существующий контроль версий; журнал привязан к подтверждённому principal, не к пользовательскому полю.
7. Ни один endpoint не принимает идентичность/роль/tenant из тела запроса или имени загруженного файла как источник полномочий.

В текущем PR эти отрицательные тесты **не добавлены как проходящие**: без настоящей авторизации это создало бы ложное свидетельство безопасности. Тест инвентаризации должен падать при добавлении нового API-маршрута до явной классификации. Текущие полномочия, схема хранения, Supabase и EPLAN Checklist не меняются.

## Архитектурное решение, которое ещё требуется

Прежде чем писать middleware, утвердить источник идентичности пользователей KD Checker, модель организаций/проектов, границу доверия (обратный прокси/сервер) и формат защищённой сессии. Дизайн PR #23 относится только к пользовательскому доступу к EPLAN Checklist и не заменяет эту работу. Не использовать общий JWT, refresh credential или service-role key между ПК.
