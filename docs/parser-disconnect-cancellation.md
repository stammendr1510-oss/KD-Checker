# Отмена parser-worker при разрыве соединения

Зависит от #86 и родителей; только защищённый стенд, не local MVP.

После полного ограниченного приёма тела `BodyBudget` создаёт доверенный
`threading.Event` в ASGI state. Единственный monitor читает настоящий transport
receive; downstream после переигрывания тела получает общий disconnect event.
Так HTTP middleware не соревнуются за одно сообщение отключения. Полученный
`http.disconnect`, ошибка transport или неожиданные сообщения после конца тела
отменяют parser work. Monitor отменяется и ожидается при обычном завершении.
При разрыве до полного приёма тела прежний отказ не запускает parser вообще.

Защищённый backend требует этот внутренний сигнал и передаёт его в `run_check`.
HTTP-поля и заголовки не могут назначить cancellation Event. Worker-parent
проверяет сигнал до spawn, во время ожидания с интервалом не более 50 мс и после
валидации результата; при отмене вызывает тот же kill/wait cleanup, что timeout.
Backend повторно проверяет сигнал перед сохранением. Отмена asyncio-задачи
также выставляет сигнал, shield сохраняет выполнение thread cleanup. Повторная
внешняя отмена может завершить ASGI-задачу раньше cleanup, но thread остаётся
ответственным за kill/reap, temp cleanup и освобождение обеих квот.

Сохранение run не выполняется после **наблюдённой** отмены. Отмена не откатывает
уже завершённую транзакцию: disconnect может быть доставлен после commit или не
доставлен reverse proxy. Поэтому клиент после сетевой ошибки должен проверить
историю, а не считать операцию обязательно несохранённой. Idempotency key для
повторной отправки здесь не добавлен. Членство по-прежнему проверяется внутри
write transaction. Глобальный timeout остаётся независимым запасным ограничением.

Это не гарантия 50 мс полного завершения: запуск interpreter, filesystem I/O,
планировщик, kill/reap и Windows Job имеют свою задержку. Лимиты входа и вывода
сохраняются. Не реализована общая дисковая/ingress квота разных HTTP-процессов,
отмена ограниченного синхронного JSON connection checker или ОС sandbox.
Нельзя объявлять Windows/two-PC acceptance пройденными по Linux тестам.

Восемь новых синтетических сценариев проверяют pre-cancel без spawn/temp, обычный
ответ без ложного disconnect/утечки monitor, broadcast disconnect и transport
failure двум downstream receivers, три реальных защищённых HTTP-сценария
(disconnect, cancel ASGI task и повторная отмена), отмену во время result validation. В HTTP тестах
настоящие auth/session/backend/SQLite и отдельный процесс с искусственно зависшим
parser; нет запрограммированных HTTP-ответов. Проверяются завершение процесса,
пустой private temp, отсутствие run, освобождение общего lock и следующая
успешная проверка настоящим движком. Оба типа отмены используют малые CSV-фикстуры.
