# KD Checker — параллельный план разработки и контроль качества

Дата: 15.11.2026. Статус: рабочий план, не декларация реализации.
Цель: развивать программу независимо от масштабной задачи Codex, исключая конфликты и неподтверждённые заявления о готовности.

## Текущий baseline

Локальный MVP FastAPI + SQLite, по умолчанию 127.0.0.1. Коды замечаний и границы доказательности описаны в `quality/rule_catalog.py`; CI-сторож `tests/test_rule_evidence_catalog.py` требует ревью новых/удалённых кодов. Каталог не подключён к runtime, отчётам или UI.

Существующие PR на момент подготовки: #23 (design сессий EPLAN Checklist), #37 (multi-PC release gates), #38 (API inventory), #40 (CSV bound), #41 (PDF bound), #42 (SQLite multi-process), #43 (restore), #44 (design RBAC). Их нельзя считать слитыми в main. Отдельная большая задача уже передана Codex; с ней нельзя конкурентно изменять те же рабочие модули без сверки.

## Единая матрица направлений

| Направление | Имеющаяся основа | Что нужно разработать | Доказательство готовности |
| --- | --- | --- | --- |
| 1. Обозначения | KD-001, KD-PE-103 | Контекстные правила именования, исключения и исходные координаты | Синтетические положительные и отрицательные кейсы; точная ссылка на источник |
| 2. Схемы/спецификации | KD-010/012, KD-PE-000/100/101/102/105 | Достоверная нормализация E3/PE3/СП, форматы источников, неопределённости | Парные данные + контроль ложных срабатываний; никакой сертификации по тексту PDF |
| 3. Соединения/кабели/клеммы | Топология из PDF не доказана | Входной контракт структурированного экспорта, граф соединений, проверяемые ограничения | Fixture структурированного источника, тесты ребёр/контактов; fail-closed при отсутствии топологии |

| 7. Междокументная согласованность | KD-PE-100/101/105, KD-SET-103 | Редакции, данные позиций и принадлежность комплекту | Один и тот же проверенный scope, явное разделение verified/unknown |

## Параллельные потоки

**Поток A, Codex (не дублировать):** основной auth/session backend, RBAC/tenant enforcement, общая БД/миграция, крупные изменения runtime, новые правила и UI, интеграционные тесты.

**Поток B, ChatGPT (текущая ветка):** инвентаризация правил, классификация доказательности, автоматические контрольные тесты контрактов замечаний, документация приёмки, независимый ревью новых PR и CI. Любой runtime-патч — лишь после проверки, что Codex не меняет соответствующий модуль.

**Поток C, инженер предприятия:** согласование ролей, модели организаций и доступа, форматов EPLAN-экспорта, требуемых редакций ГОСТ, установка и двухкомпьютерная приёмка. Не подменять это CI.

## План этапов и критерии остановки

### Этап 0 — доказуемая базовая стабильность
- Все PR сверить с актуальным main, dependency graph и CI Windows/Linux.
- Синтетические данные, отчёты, сохранение/восстановление; незакрытые блокеры документировать.
- Нет автоматического merge или работы с production.

### Этап 1 — auth и multi-tenant (P0)
- Источник identity и membership согласован.
- Гость получает 401; недостаточная роль — 403; чужой run не раскрывается.
- Все API/экспорты/сравнения защищены, обе стороны сравнения авторизованы.
- Сессии изолированы; expiry/revoke/logout, CSRF и конкуренция испытаны.
- До этого сервер доступен только локально.

### Этап 2 — центральное хранение (P0)
- Транзакционная схема без общей SQLite на сетевом диске.
- Миграция и откат, двойные записи, optimistic concurrency, резервирование и реальное восстановление на стенде.
- Отдельная проверка целостности и недоступности чужих данных.

### Этап 3 — инженерные проверки (P1)
- Каждое правило имеет код, источник/место, scope, категорию доказательности и синтетические контрпримеры.
- Топологические проверки запрещены без достоверного структурированного источника.
- Никаких новых «подтверждённых» ГОСТ-ошибок без конкретного нормативного основания и review.

### Этап 4 — интерфейс/экспорты (P2)
- История и статусы без переноса старых решений в новые runs.
- CSV/XLSX формулы инертны; отчёт строится из замороженной истории.
- Состояние Checklist всегда относится к моменту run.

### Этап 5 — выпуск для предприятия (P3)
- Windows/Linux CI зелёный; отдельная ручная проверка двух Windows ПК.
- TLS/reverse proxy, секреты, сетевые права, backup/restore, audit, rollback, эксплуатационные инструкции.
- Готовность только по доказательствам G1–G7 (см. PR #37), не по проценту закрытых задач.

## Риски и запреты

Нельзя изменять работающий EPLAN Checklist, Supabase Auth/RLS/БД, пользоваться service-role как обходом, покупать API/кредиты, отправлять реальные КД внешним сервисам, открывать локальный MVP в LAN, объединять PR автоматически. Не включать автоматическое обновление общей сессии или stale fallback. Не выдавать CI и design за промышленную приёмку.

## Как принимать каждый PR

Для каждого PR записать: SHA базы и головы, список файлов, независимость от других PR, конкретные проверяемые условия, результаты Windows/Linux CI, локальные тесты (если запускались), изменения runtime/БД, миграция/откат, безопасность, границы доказательности, оставшиеся неизвестные пункты и рекомендацию merge/no merge.

Результаты, которые нельзя независимо проверить, маркировать «не указано» или «со слов автора».
