# Офлайн-проверка staging-импорта истории KD Checker

После PR #56 можно создать проверенную копию старой истории и новый scoped staging. Этот модуль — дополнительный диагностический этап **перед ручной приёмкой**, не автоматическое восстановление.

Функция `quality.staging_import_preflight.verify_staging_import(staging_path, verified_backup=...)` открывает файлы только для чтения и возвращает ограниченный JSON-совместимый результат `{ok, problems, counts, backup_checked}`. Данные проектов, акторов, документов, комментариев и токенов не включаются в сообщения.

## Проверяемые условия

- SQLite `integrity_check` и `foreign_key_check` для staging.
- Ожидаемая версия scoped schema 1, ровно один `import_manifest`, валидный SHA-256 и явное назначение org/project/revision/operator.
- Все перенесённые runs относятся к назначенному проекту, импорту и `legacy_unknown`. Автор импортированных событий — `legacy_unknown`, а не оператор запуска.
- Разрешённые таблицы legacy-архива, корректность JSON и последовательность archive ordinal.
- Совпадение идентификаторов запусков и количества замечаний/событий в staging с архивом.
- Непрерывность цепочек аудита по версиям и соответствие итогового состояния.
- Если передана проверенная резервная копия: SHA-256 **самих байтов копии** должен совпадать с манифестом; все строки разрешённых legacy-таблиц сверяются с архивом по порядку.

## Ограничения доказательства

`backup_checked: false` означает, что внешнее сопоставление с копией не выполнено: успешный структурный отчёт не подтверждает происхождение данных. Даже при `backup_checked: true` SHA-256 показывает совпадение файлов, **но не подлинность самой исходной истории**. Для сильных гарантий нужна отдельно доверенная цепочка происхождения/хранения резервных копий.

Проверять только **доверенные остановленные локальные копии**, без других писателей и сетевых общих дисков SQLite. Инструмент не изменяет, не запускает или не подключает production-базу. Никакого HTTP-маршрута, автоматического переключения БД, миграции PostgreSQL или поддержки native EPLAN.

При неизвестной схеме или повреждении — отказ. Для многоэтапного импорта, смешанных организаций, значительных объёмов и физического восстановления на двух ПК нужна отдельная эксплуатационная процедура.

## Локальная проверка

`python -m pytest -q tests/test_staging_import_preflight.py`

Тесты создают временную синтетическую legacy-историю, staging и backup. Дополнительно проверяют удалённую строку архива, подменённую историю, неверный манифест, неподходящий backup, несуществующие входы и отсутствие побочных изменений. Для полного доказательства интеграции обязателен Windows/Linux CI.

Зависимости: #56, #45 и #55. PR основан на #56 и временно сравнивается с `main` только для штатного CI. Собственные изменения — диагностический модуль, тесты и документация. Не объединять раньше зависимостей и ручного review. Работа не использует платные API, Supabase, EPLAN Checklist или реальные данные предприятия.
