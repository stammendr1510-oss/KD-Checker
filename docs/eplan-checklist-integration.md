# EPLAN Checklist — безопасный первый этап интеграции

Этот этап добавляет **адаптер получения и валидации актуального снимка** требований
из EPLAN Checklist. Он пока **не подключён к /api/check и не показывает пункты в UI**:
до включения необходим защищённый read-only endpoint, модель доступа и
сохранение снимка вместе с результатом конкретной проверки. Прямой доступ к
Supabase по секретному ключу в клиентском приложении запрещён.

## Проверенная структура источника (14.11.2026)

В подключённом проекте EPLAN Checklist таблицы `public.sections` и
`public.items`; на дату анализа — 72 пункта в четырёх разделах.
Поля: `items.id`, `section_id`, `title`, `position` и
`sections.id`, `tab`, `title`, `position`.
Это контекст требований, а **не SQL-дамп**, не копия реальных требований и не
настройка подключения к секретным данным.

## Контракт будущего защищённого HTTPS endpoint

При каждом запуске проверки KD Checker будет выполнять GET к защищённому
`KD_CHECKLIST_FEED_URL` с отдельным узкопривилегированным токеном
`KD_CHECKLIST_FEED_TOKEN` в `Authorization: Bearer`. Его нужно создать
в серверной интеграции. **Не использовать Supabase service_role**, не
публиковать значения токенов и не задавать их в репозитории.

Пример искусственного ответа:

```json
{
  "items": [
    {
      "id": 1,
      "section_id": 4,
      "section_title": "Документы",
      "title": "Проверить комплект",
      "tab": 2,
      "position": 1
    }
  ]
}
```

Только текущие, разрешённые пользователю пункты должны входить в ответ:
сайт-источник отвечает за фильтрацию активных записей и контроль прав.
Endpoint должен возвращать **полный согласованный снимок** без постраничного
урезания и с гарантированным контролем доступа. Для будущего расширения
нужно отдельно определить, как отмечать архивные, удалённые и недействующие
пункты. Сейчас в изученной таблице `items` флага активности нет.

`checklist_snapshot.fetch_current_checklist()` проверяет HTTPS,
требует токен, отключает редиректы, ограничивает время/объём ответа,
проверяет структуру, сортирует пункты и вычисляет SHA-256 `revision`
по содержимому. При каждом вызове делает новый запрос; **нет fallback к
кэшу и нет заявления об актуальности при недоступном сервере**.
Старые результаты должны сохранять полученный в момент проверки снимок;
данный PR пока не меняет SQLite.

`planned_checklist_reviews()` создаёт безопасное представление:
все пункты отображаются как `manual_review`, никто автоматически не
признаётся выполненным. Связь с детерминированными проверками будет
добавляться отдельно, только по утверждённым правилам.

## Следующие необходимые PR

1. Согласовать безопасный endpoint с разграничением доступа и реализовать
   его отдельно от открытого браузерного клиента; сайт и базу без
   одобрения не изменять.
2. Добавить получение снимка **на каждый /api/check**, сохранение его
   идентификаторов, формулировок, хэша и времени вместе с проверкой;
   корректную обработку отказа сети, не выдавая её за успех.
3. Отобразить все текущие пункты и их статусы в интерфейсе и отчёте.
4. Связать известные правила KD Checker с конкретными `items.id`
   и сохранять доказательства; изменения пунктов требуют ревизии
   соответствующего сопоставления инженером.

Тесты используют исключительно синтетические записи. Исходные документы
предприятия не добавляются в GitHub.

## Реализация следующего этапа: снимок каждого запуска (PR после #13)

В `/api/check` добавлено получение свежего снимка при **каждом** запуске,
если настроены обе переменные окружения `KD_CHECKLIST_FEED_URL` и
`KD_CHECKLIST_FEED_TOKEN`. Без настроенного защищённого endpoint
обычные проверки КД продолжают работать, но показывается явный статус
`not_configured`; при ошибке связи — `unavailable` без старых пунктов;
при получении данных — `verified` с `revision`, `retrieved_at`,
полным перечнем пунктов и пометками `manual_review`.

В SQLite добавляется **только при первом настроенном запуске** отдельная
таблица `checklist_run_snapshots` с JSON-снимком, привязанным к `run_id`.
Старые записи, схемы `runs`/`finding_states` и экспорт Excel/CSV не
изменяются. Старые запуски показывают `not_configured`. Вкладка «История»
и результаты нового запуска показывают состояние EPLAN Checklist.

**Не реализовано пока:** фактический защищённый endpoint в действующем
Supabase, настройка его авторизации, автоматические правила по пунктам,
ручные статусы самого сайта и экспорт отдельного отчёта. Наличие
`verified` подтверждает только получение списка, **не соответствие КД**.
Секреты хранятся только в окружении локального сервера, никогда в браузере.

Прототип нужно объединять в `main` после прохождения CI Windows/Linux
и разрешения владельца. Для реальной синхронизации потребуется отдельно
разработать и согласовать защищённый read-only endpoint.
