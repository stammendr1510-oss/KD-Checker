# EPLAN Checklist — безопасный первый этап интеграции

Интеграция включает **адаптер получения и валидации актуального снимка** требований
из EPLAN Checklist и прототип привязки снимка к `/api/check`, истории и XLSX.
Для работы с реальными пунктами необходим отдельный защищённый read-only endpoint
и согласованная модель доступа. Прямой доступ к
Supabase по секретному ключу в клиентском приложении запрещён.

## Проверенная структура источника (14.11.2026)

В подключённом проекте EPLAN Checklist таблицы `public.sections` и
`public.items`; на дату анализа — 72 пункта в четырёх разделах.
Поля: `items.id`, `section_id`, `title`, `comment`, `url`, `position` и
`sections.id`, `tab`, `title`, `position`. Изменения названия, комментария
или ссылки фиксируются в контрольной сумме снимка.
Это контекст требований, а **не SQL-дамп**, не копия реальных требований и не
настройка подключения к секретным данным.

## Контракт будущего защищённого HTTPS endpoint

При каждом запуске проверки KD Checker будет выполнять GET к защищённому
`KD_CHECKLIST_FEED_URL` с отдельным узкопривилегированным токеном
`KD_CHECKLIST_FEED_TOKEN` в `Authorization: Bearer`. Его нужно создать
в серверной интеграции. **Не использовать Supabase service_role**, не
публиковать значения токенов и не задавать их в репозитории.

Пример искусственного ответа:

```json
{
  "items": [
    {
      "id": 1,
      "section_id": 4,
      "section_title": "Документы",
      "title": "Проверить комплект",
      "comment": "Проверить по выпущенной документации",
      "url": "",
      "tab": 2,
      "position": 1
    }
  ]
}
```

Только текущие, разрешённые пользователю пункты должны входить в ответ:
сайт-источник отвечает за фильтрацию активных записей и контроль прав.
Endpoint должен возвращать **полный согласованный снимок** без постраничного
урезания и с гарантированным контролем доступа. Для будущего расширения
нужно отдельно определить, как отмечать архивные, удалённые и недействующие
пункты. Сейчас в изученной таблице `items` флага активности нет.

`checklist_snapshot.fetch_current_checklist()` проверяет HTTPS,
требует токен, отключает редиректы, ограничивает время/объём ответа,
проверяет структуру, сортирует пункты и вычисляет SHA-256 `revision`
по содержимому. При каждом вызове делает новый запрос; **нет fallback к
кэшу и нет заявления об актуальности при недоступном сервере**.
Снимок текущего запуска хранится независимо от будущих правок чек-листа;
создаётся отдельная таблица в локальной SQLite для новых проверок.

`planned_checklist_reviews()` создаёт безопасное представление:
все пункты отображаются как `manual_review`, никто автоматически не
признаётся выполненным. Связь с детерминированными проверками будет
добавляться отдельно, только по утверждённым правилам.

## Следующие необходимые этапы

1. Согласовать защищённый endpoint с разграничением доступа; не изменять
   действующий сайт и Supabase без отдельного одобрения.
2. Провести испытание фактической синхронизации с авторизованным источником.
3. Связать утверждённые инженерные правила KD Checker с конкретными `items.id`
   и сохранять доказательства; изменения пунктов требуют ревизии
   соответствующего сопоставления инженером.
4. Добавить решения конструктора по ручным пунктам и согласовать жизненный цикл
   этих решений по версиям требований.

Тесты используют исключительно синтетические записи. Исходные документы
предприятия не добавляются в GitHub.

## Реализация следующего этапа: снимок каждого запуска (PR после #13)

В `/api/check` добавлено получение свежего снимка при **каждом** запуске,
если настроены обе переменные окружения `KD_CHECKLIST_FEED_URL` и
`KD_CHECKLIST_FEED_TOKEN`. Без настроенного защищённого endpoint
обычные проверки КД продолжают работать, но показывается явный статус
`not_configured`; при ошибке связи — `unavailable` без старых пунктов;
при получении данных — `verified` с `revision`, `retrieved_at`,
полным перечнем пунктов и пометками `manual_review`.

В SQLite добавляется **только при первом настроенном запуске** отдельная
таблица `checklist_run_snapshots` с JSON-снимком, привязанным к `run_id`.
Старые записи и схемы `runs`/`finding_states` не изменяются,
существующий CSV остаётся прежним, а XLSX дополняется новым листом. Старые запуски показывают `not_configured`. Вкладка «История»
и результаты нового запуска показывают состояние EPLAN Checklist.

**Не реализовано пока:** фактический защищённый endpoint в действующем
Supabase, настройка его авторизации, автоматические правила по пунктам,
ручные статусы самого сайта и отдельный экспорт только пунктов чек-листа. Наличие
`verified` подтверждает только получение списка, **не соответствие КД**.
Секреты хранятся только в окружении локального сервера, никогда в браузере.

Прототип нужно объединять в `main` после прохождения CI Windows/Linux
и разрешения владельца. Для реальной синхронизации потребуется отдельно
разработать и согласовать защищённый read-only endpoint.

## Просмотр истории и экспорт XLSX

Список `GET /api/runs` возвращает отдельные `checklist_status` и
`checklist_revision` для каждого запуска; пользователь видит их в
колонке «EPLAN Checklist» истории. Скачанный Excel-отчёт дополнен
листом «EPLAN Checklist», если для запуска есть состояние синхронизации.
На листе отражаются зафиксированные **при той проверке** статус,
причина, время, хэш редакции, список пунктов с ручным статусом,
их комментарии и ссылки как обычные текстовые поля.
Экспорт никогда не выполняет новый сетевой запрос. Поля формируются
как текст (в том числе формулоподобные строки требований), чтобы
недоверенный текст не становился формулой Excel.

Этот лист **не означает успешное прохождение требований**; даже при
статусе `verified` все пункты пока требуют инженерного подтверждения.

## Сравнение редакций EPLAN Checklist в истории

API `GET /api/runs/{current_id}/checklist-compare/{previous_id}` показывает
изменения **содержания требований**, сохранённых в двух исторических проверках:
добавленные и удалённые пункты по стабильному `id`, а также изменения
названия, раздела, порядка, комментария и ссылки. При открытии истории
есть отдельное сравнение версий чек-листа.

Сравнение **не выполняется и не выдаёт результат**, если хотя бы один
снимок имеет статус `not_configured` или `unavailable` (либо у старой
проверки не было снимка). Изменения чек-листа не означают несоответствие КД
и не изменяют инженерные решения, историю файлов или статусы замечаний.
Тексты требований в браузере экранируются. Используются только сохранённые
данные: запрос к EPLAN Checklist при историческом сравнении не выполняется.

## Поиск по архивному чек-листу

В интерфейсе после успешного получения снимка требования группируются по
вкладкам и разделам (идентификаторы `tab`/`section_id`). Добавлен
локальный поиск по формулировкам, идентификаторам, комментариям и ссылкам,
работающий и для исторических запусков. Фильтр меняет только отображение;
он не меняет источник, не записывает решения инженера и не делает сетевые
запросы. При отсутствии подтверждённого снимка фильтр не показывается.
Каждый пункт остаётся с честной пометкой «Требует проверки инженером».

## Необязательный прямой источник Supabase с RLS

Дополнительно реализован **отключённый по умолчанию** read-only путь из
существующего Supabase Data REST API. Он не требует Edge Functions,
изменений сайта, SQL-миграций и ключа администратора. Сервер KD Checker
использует только три переменные окружения, задаваемые владельцем
локальной установки:

- `KD_CHECKLIST_SUPABASE_URL`: HTTPS URL проекта `https://<ref>.supabase.co`
- `KD_CHECKLIST_SUPABASE_PUBLISHABLE_KEY`: только `sb_publishable_...`
- `KD_CHECKLIST_SUPABASE_USER_JWT`: **краткосрочный access JWT
  уже авторизованного пользователя**, не пароль и не service_role.

Секрет JWT не отправляется браузеру KD Checker, не сохраняется в SQLite
и не пишется в журнал. Срок действия токена определяется Supabase Auth:
при истечении требуется новый авторизованный токен, иначе новый запуск
имеет статус `unavailable` и не использует старый список. **Автоматическое
обновление JWT не реализовано**; не настраивайте эту схему как постоянное
безнадзорное подключение, пока не появится безопасная процедура обновления.
Не сохраняйте ключи и JWT в GitHub, конфигурационных JSON или скриншотах.

Выполняется ровно один GET `/rest/v1/items` с объединённым разделом
`sections!inner`, ограничением 2001 запись, `Prefer: count=exact`
и `Content-Range`. Сервер обязан подтвердить полный набор: при
неполной выборке, пустом ответе, отсутствии прав/сессии,
неверном формате или повторном ID проверка считается `unavailable`.
Таблицы `public.items` и `public.sections` должны разрешать
чтение данному конкретному пользователю через grants и RLS.
**Publishable key не даёт разрешение сам по себе.**

Если одновременно заданы настройки старого HTTPS feed и прямого Supabase,
программа сообщает об ошибке источника (без неявного выбора одного из них).
Никаких POST/PATCH/SQL-записей этот путь не выполняет. Два варианта источника
используют одинаковые форматы архива, ревизии и ручных пунктов.

Этот этап протестирован **на синтетических ответах** с подставным
HTTP-клиентом, без реального входа и запроса к действующему проекту.
Реальная возможность чтения и безопасность доступа конкретного пользователя
нуждаются в отдельной проверке после безопасной локальной настройки.
Никаких платных функций сторонних сервисов подключать не требуется; однако
перед эксплуатацией владелец должен убедиться, что используется допустимый
бесплатный тариф/лимит Supabase.

### Строгая проверка полноты диапазона

При чтении Supabase ответ принимается только с явно подтверждённым
`Content-Range` вида `0-(N-1)/N`, где `N` равно фактически полученному
числу записей, ограничено `MAX_ITEMS` и не равно нулю. Смещённые,
обрезанные и противоречивые диапазоны отклоняются, даже если JSON выглядит
правильно. Запрос передаёт `Cache-Control: no-store` и `Pragma: no-cache`;
при недоступности источника старые снимки не используются.

## Подробный просмотр изменений редакций

Экран сравнения двух исторических подтверждённых снимков раскрывает для каждого
изменённого требования **конкретные значения «Было» / «Стало»** по каждому
изменившемуся полю: формулировка, комментарий, ссылка, раздел, вкладка и порядок.
Ссылки отображаются только как безопасный текст, а все значения экранируются.
Пустые строки помечаются прочерком. Это исключительно сравнение данных;
никаких новых выводов о соответствии КД и никаких сетевых запросов нет.
