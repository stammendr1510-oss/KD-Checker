## 1. Задача блока 3

Э3 содержит не только позиционные обозначения изделий, но и идентификаторы
контактов, выводов, адресов соединений и перекрёстных ссылок. Если считать
каждый такой токен самостоятельным изделием, KD-PE-105 начинает требовать в
ПЭ3 позиции, которых там быть не должно.

Блок 3 вводит явную классификацию извлечённых идентификаторов. Проверка
наличия в ПЭ3 допускается только для `device_candidate`. Выводы, адреса
соединений и ссылки сохраняются как свидетельство возможного присутствия, но
не порождают отдельное замечание об отсутствии изделия.

## 2. Категории

| Категория | Смысл | Допускается к проверке наличия в ПЭ3 | Свидетельство присутствия | Требует контекста |
|---|---|---|---|---|
| `device_candidate` | полное самостоятельное позиционное обозначение | да | да | нет |
| `terminal_or_pin` | вывод, контакт или точка клеммника | нет | да, для родительского устройства | нет; контекст нужен, чтобы считать родителя самостоятельным изделием |
| `connection_reference` | конец электрического соединения / адрес | нет | да | нет |
| `cross_reference` | ссылка на устройство в другом месте | нет | да | нет |
| `ambiguous` | доказательств недостаточно | нет | нет | да |

Категория хранится вместе с исходным токеном, нормализованным обозначением,
родительским устройством, выводом и причиной классификации
([`ClassifiedIdentifier`](../identifier_classification.py:129)).

## 3. Примеры из постановки

| Фрагмент | Исходный токен | Нормализованное обозначение | Категория | Родительское устройство | Вывод | Причина |
|---|---|---|---|---|---|---|
| `1KM1` | `1KM1` | `1KM1` | `device_candidate` | — | — | `bare_designation` |
| `1KM1:A1` | `1KM1:A1` | `1KM1:A1` | `terminal_or_pin` | `1KM1` | `A1` | `explicit_pin_separator` |
| `1HLW:X1` | `1HLW` | `1HLW` | `terminal_or_pin` | `1HLW` | `X1` | `pin_reference_in_context` |
| `X1` | `X1` | `X1` | `ambiguous` | — | — | `ambiguous_terminal_family` |
| `XT4.2` | `XT4.2` | `XT4.2` | `terminal_or_pin` | `XT4` | `2` | `dotted_pin_suffix` |
| `3TA2` | `3TA2` | `3TA2` | `device_candidate` | — | — | `bare_designation` |
| `SF1:1 - XT1:2` | `SF1` / `XT1` | `SF1` / `XT1` | `connection_reference` | `SF1` / `XT1` | `1` / `2` | `connection_endpoint` |
| `см. QF1` | `QF1` | `QF1` | `cross_reference` | — | — | `cross_reference_marker` |

Примеры не являются универсальными правилами: классификатор учитывает полный
текст строки, соседние подписи и структурные признаки токена.

## 4. Правила классификации

Порядок проверок в
[`classify_identifier()`](../identifier_classification.py:215):

1. Явный разделитель вывода `:` внутри токена (`1KM1:A1`) → `terminal_or_pin`.
2. Точечный суффикс `.N`, где префикс является полным обозначением
   (`XT4.2`, `3TA2.1`) → `terminal_or_pin`.
3. В строке после токена стоит `:вывод` (`1HLW:X1`, в том числе при переносе
   PDF-слова) → `terminal_or_pin`.
4. Строка содержит соединение двух выводов (`SF1:1 - XT1:2`) →
   `connection_reference` для обоих концов.
5. Строка содержит маркер ссылки/примечания (`см.`, `поз.`, `лист`,
   `документ`, номер документа, `Э3`/`ПЭ3`) → `cross_reference`.
6. Токен находится в примечании или табличном фрагменте → `ambiguous`.
7. Полное обозначение без признаков вывода/ссылки → `device_candidate`.
8. Иное → `ambiguous`; токен не удаляется.

### 4.1. Почему правила не привязаны к буквенным кодам

Классификация опирается на структуру (`:`, `.N`, соединение, маркер ссылки,
контекст строки), а не на список «изделий». Специальное правило только одно:
одиночное обозначение семейства `X` считается `ambiguous`, потому что
существующая модель типов описывает `X` как «клеммник/соединение». Это
единственное семейство с такой двойственностью; `XT`, `XN`, `XL`, `XG`
остаются кандидатами в изделия. Коды `KM`, `QF`, `TA`, `SF`, `HLG`, `HLW` и
другие не имеют специальных правил.

## 5. Отчёт: что допускается к проверке наличия в ПЭ3

Функция [`classification_report()`](../identifier_classification.py:321)
возвращает три явных списка:

- `eligible_for_presence_check` — только `device_candidate`;
- `presence_evidence_only` — `terminal_or_pin`, `connection_reference`,
  `cross_reference`;
- `requires_context` — `ambiguous`.

Пример:

```python
from identifier_classification import classification_report

report = classification_report(mentions)
report["eligible_for_presence_check"]  # ["1KM1", "3TA2", ...]
report["presence_evidence_only"]       # ["1HLW", "SF1", "XT1", "XT4.2", ...]
report["requires_context"]             # ["X1", "ABC", ...]
```

В [`e3_pe3_inventory.py`](../e3_pe3_inventory.py) доступна обёртка
[`classification_summary()`](../e3_pe3_inventory.py:341).

### 5.1. Что требует дополнительного контекста

- `X1` и другие одиночные обозначения семейства `X`;
- токены, не являющиеся полным позиционным обозначением (`ABC`);
- обозначения в примечаниях и табличных фрагментах без явной ссылки;
- любые иные случаи, где структурных признаков недостаточно.

Такие обозначения сохраняются как `ambiguous` и не превращаются в
самостоятельные изделия. В структурированных деталях они получают причину
`needs_context`.

## 6. Интеграция с KD-PE-105

`SchemeComponent` хранит поля классификации: `category`,
`classification_reason`, `parent_device`, `eligible_for_presence_check`,
`presence_evidence`, `requires_context`.

[`compare_inventories()`](../e3_pe3_inventory.py:666) делит компоненты так:

| Классификация | Куда попадает | Может ли дать замечание об отсутствии изделия |
|---|---|---|
| `device_candidate` | `missing` / `matched` | да, по правилам блока 2 |
| `terminal_or_pin` | `reference_only` | нет |
| `connection_reference` | `reference_only` | нет |
| `cross_reference` | `reference_only` | нет |
| `ambiguous` | `ambiguous` или предположительная проверка | нет warning; сохраняется для инженера |

Дополнительные инварианты:

- вывод устройства не создаёт отдельное замечание об отсутствии изделия;
- если обозначение устройства встречается в допустимой ссылке на контакт,
  оно используется как свидетельство присутствия: при наличии в ПЭ3 считается
  сопоставленным, при отсутствии — попадает в `reference_only`, а не в
  `missing`;
- `ambiguous` никогда не даёт `warning`;
- `confidence` для `ambiguous` не выше `medium`;
- схема `details` v1 не расширялась полями; добавлено только значение причины
  `needs_context` для элементов `ambiguous`;
- `KD-PE-100`–`KD-PE-104`, CSV/Excel, SQLite и история не изменялись.
