# KD-PE-105: инженерное представление доказательств (блок 5)

Дата: 21.11.2026. Продолжение блоков 1–4
([`kd-pe-105-diagnostics.md`](kd-pe-105-diagnostics.md),
[`kd-pe-105-matching-evidence.md`](kd-pe-105-matching-evidence.md),
[`kd-pe-105-contextual-classification.md`](kd-pe-105-contextual-classification.md),
[`kd-pe-105-confidence-model.md`](kd-pe-105-confidence-model.md)).

Модуль представления: [`kd_pe_105_evidence.py`](../kd_pe_105_evidence.py).
Тесты: [`tests/test_kd_pe_105_evidence.py`](../tests/test_kd_pe_105_evidence.py).

## 1. Задача

Блоки 1–4 сделали выводы KD-PE-105 объяснимыми на уровне модели, но инженер
видел в интерфейсе и Excel в основном JSON и короткий список обозначений.
Блок 5 добавляет **человекочитаемое доказательство**, не меняя схему `details`
v1, шестиколоночный CSV и историю решений.

Критерий: по каждому замечанию инженер определяет источник, уровень
достоверности и необходимое действие без ручной расшифровки JSON.

## 2. Где формируется представление

`details` schema v1 остаётся единственным источником. Представление
`evidence_view` **вычисляется на чтении** и не сохраняется в SQLite:

- [`app.run()`](../app.py) обогащает ответ `GET /api/runs/{id}`;
- [`ScopedBackend._dispatch()`](../secure_backend.py) обогащает ответ
  защищённого рабочего места;
- [`excel_reports.build_excel_report()`](../excel_reports.py) строит
  человекочитаемый текст из того же модуля.

Сохранённые замечания, fingerprint, решения инженера и журнал изменений не
меняются. Повторное открытие старой проверки даёт тот же `details` и тот же
`evidence_view`.

## 3. Поля представления

| Поле | Смысл |
|---|---|
| `detected`, `detected_count` | обнаруженные обозначения и их полное число |
| `e3.document`, `e3.pages_text` | исходный документ Э3 и подтверждённые листы |
| `pe3.document`, `pe3.page`, `pe3.table_row`, `pe3.row_confirmed` | документ ПЭ3, лист и только подтверждённая строка таблицы |
| `pe3.quantity`, `pe3.entries_count`, `pe3.name` | количество, число раскрытых обозначений, наименование позиции |
| `reason`, `reason_label`, `reason_explanation` | характер расхождения |
| `confidence`, `confidence_label` | итоговая достоверность |
| `confidence_basis` | причина достоверности по сохранённым признакам |
| `what_is_missing` | чего не хватило для достоверного вывода |
| `candidates`, `candidate_count` | несколько кандидатов сопоставления, если они есть |
| `classification` | изделие, контакт/клемма/ссылка или неопределённый случай |
| `recommendations` | рекомендации инженеру |
| `items` | доказательства по каждому обозначению: листы, вид упоминания, фрагменты |
| `ambiguous` | неоднозначные обозначения с причиной |
| `notes` | ограничения отображения |

### 3.1 Координаты PDF

Представление **не содержит** `bbox_pt` и `pe3_row_band_pt`. Показываются
только:

- лист PDF, полученный из проверенной строки ПЭ3;
- номер строки таблицы, если он подтверждён сеткой PDF.

Если сетка не подтверждена, интерфейс и Excel явно пишут «строка таблицы не
подтверждена», а не угадывают номер по близости текста. Структурированный JSON
в отдельной колонке Excel сохраняет исходные координаты, прошедшие валидатор.

## 4. Контрольные примеры

### TA

Для подтверждённого дефекта TA инженер сразу видит:

- `3TA2`, `3TA3`;
- документ и листы Э3;
- документ ПЭ3, лист и строку таблицы;
- количество 9 и 7 раскрытых обозначений;
- причину `quantity_mismatch` и высокую достоверность;
- рекомендацию дополнить перечень.

### KM

Для KM с одной похожей строкой показывается:

- `3KM2`;
- строка ПЭ3 присутствует, но помечена как **не доказывающая принадлежность**;
- причина `row_matched_without_coverage`;
- средняя достоверность;
- «не хватает доказательства принадлежности: совпали только тип и группа».

Инженер видит, почему строка ПЭ3 не может считаться однозначной.

### X/XT

Поле `classification` различает:

- `product` — самостоятельное изделие, проверяется наличие в ПЭ3;
- `contact_or_terminal` — вывод, контакт, клемма или ссылка;
- `undefined` — недостаточно контекста.

Для семейств `X`, `XT`, `XN`, `XL`, `XG` результат остаётся информационным;
инженер видит, является ли запись изделием, контактом/клеммой или
неопределённым случаем.

## 5. Неоднозначные кандидаты

Схема `details` v1 не хранит строки-кандидаты. Чтобы не расширять схему,
производитель добавляет в `message` и `location` ограниченную строку:

```text
Кандидаты ПЭ3: лист PDF 2, строка таблицы 5; лист PDF 2, строка таблицы 7.
```

Представление извлекает её и показывает список. Если строка не подтверждена
сеткой, пишется «строка не подтверждена», а не выдуманный номер. Если в
будущем появится `details["candidates"]`, представление использует его в
приоритетном порядке.

## 6. Интерфейс

Оба интерфейса показывают блок «Структурированные сведения»:

- локальное рабочее место: [`static/index.html`](../static/index.html);
- защищённое рабочее место: [`secure_static/workbench.js`](../secure_static/workbench.js).

Разделы:

1. обнаруженные обозначения;
2. документы и листы Э3/ПЭ3;
3. лист и подтверждённая строка ПЭ3;
4. тип и классификация результата;
5. характер расхождения;
6. достоверность и причина достоверности;
7. чего не хватило;
8. кандидаты ПЭ3;
9. рекомендации инженеру;
10. доказательства по обозначениям;
11. неоднозначные обозначения и примечания.

Длинные обозначения переносятся (`overflow-wrap:anywhere`). Списки
ограничены: до 50 обозначений в кратком перечне и до 200 в блоке
доказательств; полный список — в Excel. Это защита DOM, а не потеря данных.

После новой проверки локальное рабочее место использует сохранённый ответ
`GET /api/runs/{id}`, поэтому `evidence_view` доступен сразу, без перехода в
историю.

## 7. Excel

Лист `Замечания` сохраняет 10 базовых колонок. При наличии `details`
добавляются две колонки:

- `Доказательства KD-PE-105` — человекочитаемый текст с разделами
  «Обнаруженные обозначения», «Документ Э3», «Документ ПЭ3», «Характер
  расхождения», «Почему такая достоверность», «Чего не хватило»,
  «Кандидаты ПЭ3», «Рекомендации инженеру», «Доказательства по обозначениям»;
- `Детали KD-PE-105 (JSON)` — компактный JSON schema v1.

Текст ограничен 30 000 символов; при большом числе элементов показываются
первые 20 обозначений и явное указание, что полный список — в JSON/исходных
документах. Все значения записываются как текст, формулы не исполняются.

## 8. CSV

CSV остаётся строго шестиколоночным:

```text
Важность;Код;Файл;Место;Замечание;Рекомендация
```

`evidence_view` в CSV не выводится. Человекочитаемые `message` и
`recommendation` не меняются. Строка кандидатов может попадать в `Место` и
`Замечание`, но число колонок не меняется.

## 9. История и решения инженера

- `details` хранится внутри JSON замечания без изменений;
- `finding_identity()` не зависит от `evidence_view`;
- решения инженера и журнал изменений не мигрируются;
- сравнение проверок работает по сохранённым замечаниям;
- обогащение выполняется только в ответе на чтение и не попадает в SQLite.

Проверки: `test_api_returns_evidence_view_without_changing_stored_schema`,
`test_engineer_decision_and_history_are_preserved`,
`test_enrich_run_does_not_mutate_the_input_record`.

## 10. Ограничения

- Представление объясняет сохранённые признаки, но не заменяет исходные
  документы.
- Если в старом отчёте нет `details`, показывается прежний блок.
- Координаты не отображаются в человекочитаемом виде; для машинной обработки
  они остаются в JSON.
- Реальные PDF предприятия в репозиторий не добавлялись.
