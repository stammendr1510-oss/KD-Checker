# Управление замечаниями, версия 1

Результат проверки и решение инженера хранятся отдельно. Уровень, код, документ,
место, описание и рекомендация остаются в исходном JSON `runs.issues`. Изменение
решения не запускает повторную проверку, не меняет её счётчики, не переписывает КД
и не изменяет существующий CSV. В Excel после прежних семи столбцов добавлены
«Статус», «Комментарий инженера», «Дата изменения».

## Решения и журнал

Во всех проверках, включая старые, замечание первоначально имеет статус «Новое»,
пустой комментарий и пустую дату изменения. Доступны также «В работе», «Устранено»
и «Отклонено с обоснованием». Для отклонения обязателен непустой комментарий.
Комментарий ограничен 4000 символами. Решение редактируется после проверки или
при открытии записи истории; кнопка «Сохранить решение» явно фиксирует выбор
инженера. «Устранено» означает решение инженера, а не новый результат алгоритма.

SQLite хранит каждое изменение статуса **или** комментария: значения до и после,
время UTC и номера версий. Повторное сохранение тех же значений не создаёт фиктивное
событие. Журнал доступен через кнопку «История изменений». Дата в интерфейсе
показана в часовом поясе браузера, в API и Excel — ISO 8601 с UTC-смещением.
Текст комментариев не исполняется как HTML или как формулы Excel.

Для защиты от потери параллельных правок API принимает `expected_version`.
Устаревшая версия получает HTTP 409. Интерфейс сохраняет несохранённый текст:
инженеру нужно открыть актуальную проверку, сравнить решения и сохранить выбор
повторно. Молчаливого перезаписывания чужой правки нет.

В первой версии нет аккаунтов, авторства изменений, защищённой электронной
подписи или журнала, защищённого от прямого редактирования файла SQLite.
Журнал устанавливает **что и когда** было изменено через приложение.
Сохраняется модель локального сервера на `127.0.0.1`; общий доступ требует
отдельной системы авторизации. Приложение не использует ChatGPT или внешние AI.

## Сопоставление повторных проверок

Каждое появление замечания имеет отдельный постоянный ID. Версия 1 отпечатка —
SHA-256 от имени документа, уровня, кода, места, полного описания и рекомендации.
Используются Unicode NFC, нормализация пробельных символов и имени файла:
без каталога, с приведением регистра, с учётом Windows-путей. Исходные строки
проверки при этом не меняются. Порядок замечаний не участвует в идентичности.

Сравнивается только последняя предыдущая проверка с тем же набором имён файлов
(их порядок не важен; кратность сохраняется). Только уникальное точное совпадение
связывается с предыдущим появлением. Дубли в любой из проверок помечаются как
неоднозначные и не связываются автоматически. Если в последней проверке замечание
отсутствовало, поиск более старого решения не выполняется.

**Статусы и комментарии не переносятся автоматически вообще.** В том числе
совпадение с «Устранено» создаёт новое появление со статусом «Новое».
Интерфейс показывает прошлый статус и комментарий только для справки; для текущей
проверки инженер выбирает статус и нажимает «Сохранить решение». Прежняя запись
и её журнал остаются самостоятельными. Отсутствие замечания в новом отчёте
также не закрывает старую запись автоматически.

Ограничения: это консервативное текстовое сопоставление, а не сравнение графики
или содержимого исходной КД. Переименование документа, другой набор файлов,
изменение текста, места, уровня или рекомендации могут разорвать связь.
Одинаковые имена файлов и одинаковый текст в разных проектах могут дать
совпадение: идентификаторов проекта и версии исходной КД в старой истории нет.
Нет нечёткого поиска и ручного связывания разных отпечатков в этой версии.
Показанная связь требует инженерной сверки и не доказывает устранение проблемы.

## Миграция и резервные копии

1. Остановите сервер и все экземпляры приложения, работающие с этой SQLite.
2. Дополнительно сохраните `data/history.sqlite3` и `config.json` в надёжном месте.
3. Новым Python приложения выполните `python storage.py --migrate-issue-management`.
   На Windows можно использовать `.venv\Scripts\python.exe` вместо `python`.
4. Запустите приложение и проверьте старую запись истории.

Миграция также автоматически выполняется при первом обращении к SQLite.
До изменения существующей схемы SQLite Online Backup создаёт рядом файл
`history.sqlite3.before-issue-management-<UTC-время>.bak`, не перезаписывая
предыдущие копии. Ошибка копирования останавливает миграцию. На новой пустой базе
исходных данных для резервирования нет.

Миграция версии 1 транзакционно добавляет `issue_schema`, `issue_runs`,
`finding_states`, `finding_events` и индексы, затем создаёт отдельные состояния
для старых замечаний. Таблица `runs`, её строки, ID, даты и JSON не переписываются.
При ошибке DDL и заполнение откатываются целиком. Повторный запуск не дублирует
состояния. Неизвестная более новая версия схемы блокирует открытие старым кодом.
Для крупной истории миграция может занять время и потребовать место под копию;
её следует выполнять до запуска сервера в режиме обслуживания.

## Откат

1. Остановите все экземпляры приложения.
2. **Пока доступен новый код**, выполните
   `python storage.py --rollback-issue-management`.
3. Команда выведет путь новой полной копии
   `history.sqlite3.before-issue-rollback-<UTC-время>.bak`.
   Убедитесь, что она сохранена: в ней остаются решения и весь журнал.
4. Верните предыдущую версию приложения и запустите её с текущей SQLite.

Команда транзакционно удаляет только четыре дополнительные таблицы управления
замечаниями. **Все проверки в `runs`, включая созданные после обновления,
сохраняются.** Статусы и журнал после отката доступны в резервной копии,
а не в старом интерфейсе. Не запускайте новый сервер между шагами 2 и 4:
он снова применит миграцию и создаст начальные состояния.

При необходимости вернуть решения сохраните текущую базу отдельно и восстановите
полную копию `before-issue-rollback` при остановленном приложении, затем запустите
новую версию. Проверки, созданные после этой копии, в неё не входят; заранее
сохраните их текущую базу. Восстановление первоначальной `before-issue-management`
тоже возможно, но потеряет в рабочей базе все проверки, созданные после её даты,
поэтому для штатного отката используйте команду выше.

## API

- `GET /api/runs/{run_id}` сохраняет прежние поля и добавляет `finding_states`;
  `issues` остаётся исходным результатом алгоритмов.
- `PATCH /api/runs/{run_id}/findings/{finding_id}` принимает `status` (`new`,
  `in_progress`, `resolved`, `rejected`), `comment`, `expected_version`.
- `GET /api/runs/{run_id}/findings/{finding_id}/history` возвращает изменения по ID
  события в порядке фиксации. Принадлежность замечания проверке проверяется.
- Неверное тело запроса — 422, неизвестное замечание в проверке — 404,
  конфликт версии — 409.

## Тесты

Все тестовые документы искусственные; база создаётся во временном каталоге.
Установите `pip install -r requirements.txt -r requirements-dev.txt`, затем
`python -m playwright install --with-deps chromium` и `python -m pytest -q`.
Для уже установленного Chromium можно задать `KD_TEST_CHROMIUM` с путём к нему.
CI выполняет весь набор, включая браузерный сценарий, на Windows и Linux.
