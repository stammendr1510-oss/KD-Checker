# Приёмочные испытания KD Checker на Windows

Этот сценарий проверяет локальную сборку и основные пользовательские операции.
Он **не** удостоверяет соответствие КД требованиям ЕСКД/ГОСТ, не проверяет
промышленную готовность и не использует действующий EPLAN Checklist.

## Подготовка

1. Используйте отдельную тестовую папку KD Checker, не заменяя работающую установку.
2. Установите Python 3.11+; на Windows используйте штатный `start_windows.bat`.
   Первый запуск может потребовать интернет только для установки зависимостей.
3. Для полностью автономного прогона **не задавайте**
   `KD_CHECKLIST_FEED_URL` и `KD_CHECKLIST_FEED_TOKEN`.
   Ожидаемый статус: «Источник не настроен» / `not_configured`,
   а не «синхронизирован».
4. Используйте только вымышленные обозначения и самостоятельно созданные PDF,
   например `ABCD.123456.001.ВО.pdf` и `ABCD.123456.001.СП.pdf`.
   Реальные документы предприятия не нужны.

## Автоматическая проверка (Windows/Linux CI)

```console
python -m pip install -r requirements.txt -r requirements-dev.txt
python -m pytest -q tests/test_acceptance_smoke.py
```

Сценарий создаёт тестовые PDF программно и временную SQLite. Он проверяет
загрузку PDF через локальный API, сохранение истории, решение инженера,
независимость статусов повторного запуска, сравнение «до/после»,
CSV/XLSX выгрузки и отказоустойчивый учёт повреждённого PDF.
Выполняется в CI на обеих ОС. Успешный CI **не означает**, что ручной
приёмочный прогон непосредственно на вашем ПК уже выполнен.

## Ручной сценарий для Windows

Отмечайте фактический результат каждого шага, не изменяя рабочие данные:

- [ ] `start_windows.bat` запускает локальный сайт на
  `http://127.0.0.1:8765`; удалённый доступ не включён
- [ ] При загрузке двух синтетических PDF ВО и СП одного обозначения
  проверка завершается и появляется история с ID запуска
- [ ] Для такого набора сводка `KD-SET-201` описывает **загруженные PDF**,
  а не подтверждает полноту выпущенной КД
- [ ] Можно изменить статус замечания на «В работе», добавить комментарий,
  открыть историю решений и увидеть его в Excel отчёте
- [ ] Повторная загрузка тех же файлов создаёт новый запуск; решение
  инженера из прежнего запуска не переносится автоматически
- [ ] Сравнение двух запусков показывает сохраняющиеся замечания;
  исчезновение замечания не объявляется подтверждённым исправлением
- [ ] Выгрузки CSV и XLSX доступны из истории и содержат замечания;
  неожиданные формулы из текста замечаний не исполняются
- [ ] Повреждённый тестовый PDF получает `KD-000`; программа не объявляет
  его успешно проанализированным комплектом
- [ ] Без настроенного Checklist в истории виден статус источника
  `not_configured`, а не отметка о полученных текущих требованиях
- [ ] Сервер можно остановить через Ctrl+C, после повторного запуска
  сохранённые результаты и комментарии доступны

## Протокол и критерии завершения

Зафиксируйте локально: дату, версию/commit, Windows и Python, исход каждого
пункта (успешно/неуспешно/не проверено), номера тестовых запусков, журнал
сбоев и принятые инженером решения. Секреты, реальные PDF и персональные
данные **не публикуйте** в GitHub.

Сценарий считается пройденным, когда все применимые пункты выполнены без
необъяснённых ошибок. Если хотя бы один пункт провален, заводится отдельная
задача с обезличенным воспроизведением. Для промышленной приёмки потребуются
отдельные измерения точности правил на согласованных эталонных комплектах,
проверка резервного копирования и восстановления, тесты отказов, безопасности
и производительности; этот smoke-тест их не заменяет.
