## 5. Оценка универсальности

### 5.1. Что действительно универсально

| Механизм | Общее условие | Не привязано к |
|---|---|---|
| Раскрытие группы | разделители `; ,` перенос, диапазон с однозначными границами | `TA2/TA3` |
| Колонка ПЭ3 | заголовок + вертикальные границы, fallback | конкретная форма |
| Текстовая защита | обозначение в тексте ПЭ3 → не missing | конкретный код |
| `KD-PE-106` | повтор + несовместимое напряжение/тип | `KLD3` |
| `KD-PE-107` | равная длина, одно различие из пары | `SO1/S01` |
| Семейства | общая структура `TAG` | `K/KA/HL` |
| Маркеры | близость к токену / документная ссылка | `лист/табл` |
| Усечение | превышение лимита | конкретная строка |

Проверено на независимых комбинациях семейств `TA, QF, KM, KLD, KA, KL, HL,
X/XT` и на модельных токенах разной структуры.

### 5.2. Где остаётся эвристика

| Место | Эвристика | Риск | Как ограничен |
|---|---|---|---|
| `TAG_PREFIX` | фиксированный список семейств | новое семейство не распознается | `non_tag_token` сохраняется, не теряется |
| `_designator_column` | заголовок `поз/обознач/позиц`, fallback 9–18.8 % | нестандартный заголовок | fallback + `ambiguous` |
| `MIN_TABLE_ROW_TOP = 50` | область заголовка | высокая шапка | консервативно, без warning |
| `VOLTAGE_RE` / `TYPE_CODE_RE` | шаблоны напряжений и типов | нестандартная запись | при отсутствии атрибута — `ambiguous`, не warning |
| `_CONFUSABLE_GROUPS` | список пар символов | редкая пара не покрыта | только `info`, без автозамены |
| `_is_cross_reference` | окно ±24 символа | очень длинная строка | документная ссылка проверяется отдельно |
| `REFERENCE_MARKER_RE` | маркер в конце фрагмента | нестандартный маркер | роль не меняется, свойство сохранено |

Вывод: правила **универсальны по условию**, но остаются **эвристическими по
полноте**. Ни одно не выдаёт warning без доказательства; неполнота приводит к
`ambiguous`/`info`, а не к ложному выводу.

### 5.3. Разделение ошибок извлечения и инженерного анализа

| Слой | Признак | Результат |
|---|---|---|
| Извлечение | нет текста, нет сетки, строка не разобрана | `not_evaluated`, `ambiguous` |
| Анализ | строка подтверждена, атрибуты несовместимы | `KD-PE-106` warning |
| Анализ | обозначение отсутствует при полном разборе | `KD-PE-105` warning |

Это ключевое требование задачи и оно выполнено: `present_in_unparsed_pe3_text`
не превращается в «изделие отсутствует».

## 7. Рекомендации для KD-PE-108: единая инженерная модель КД

Текущие правила добавлялись точечно и теперь покрывают больше случаев, но
остаются набором эвристик. Следующий шаг — **не переписывание архитектуры**, а
введение единой инженерной модели документа, на которую постепенно
переводятся существующие правила.

### 7.1. Модель документа

```text
Документ → Лист → Строка → Ячейка → Токен
                                   ↓
                          Обозначение (designation)
                                   ↓
                          Изделие (product) + Атрибуты
```

- **Токен** — как он извлечён (сырое значение, координаты, лист).
- **Обозначение** — нормализованное позиционное обозначение.
- **Изделие** — сущность с атрибутами: тип, наименование, напряжение,
  количество, позиция, листы, ссылки.
- **Роль появления** — `label`, `reference`, `note`, `table`, `pin`,
  `connection` — отдельный атрибут, не заменяет свойство обозначения.

### 7.2. Слои

| Слой | Ответственность | Детерминизм |
|---|---|---|
| Извлечение | слова, линии, ячейки, координаты | да |
| Нормализация | регистр, кириллица/латиница, разделители | да, без автозамены |
| Модель | документ/строка/ячейка/изделие | да |
| Правила | предикат + доказательство + уровень | да |
| Представление | JSON/Excel/CSV/UI | да |

### 7.3. Реестр правил как данные

Каждое правило описывается декларативно:

```text
id, версия, условие (предикат), обязательные доказательства,
уровень по умолчанию, политика неопределённости, ссылка на тесты
```

Это позволит:

- проверять полноту каталога автоматически;
- не добавлять код для каждого нового семейства;
- явно видеть, какие правила требуют реального подтверждения.

### 7.4. Единая модель неопределённости

Сохранить дискретные уровни доказательств и правило минимума, но вынести их в
общую модель:

- `extraction` — качество извлечения;
- `identity` — однозначность обозначения;
- `attribution` — принадлежность строки;
- `attribute` — полнота атрибутов.

Итоговый уровень — минимум по обязательным факторам. Числовые веса не
вводить без размеченного корпуса.

### 7.5. Атрибутная модель изделия

Вместо сравнения строк — сравнение атрибутов:

- `type_code`, `voltage`, `current`, `poles`, `quantity`, `position`;
- конфликт — несовпадение атрибута с ненулевой уверенностью;
- отсутствие атрибута — `unknown`, не конфликт.

Это расширит `KD-PE-106` без привязки к напряжению и типу.

### 7.6. Топология как отдельный уровень

Соединения, клеммы и кабели — отдельная модель (`netlist`), не смешанная с
перечнем элементов. Существующие `KD-CON-*` остаются прототипом до появления
структурированного источника.

### 7.7. Нормативные требования как каталог

ГОСТ/ЕСКД — данные (каталог требований), а не код. Правило ссылается на пункт
нормы; отсутствие пункта — `NOT VERIFIED`, а не «соответствует».

### 7.8. Приёмка и метрики

- эталонный синтетический комплект (уже есть) — регрессия;
- размеченный корпус реальных КД — precision/recall по категориям;
- запрет на повышение уровня без подтверждённого корпуса;
- протокол приёмки с фиксированным SHA и средой.

### 7.9. Порядок внедрения

1. Вынести модель `Документ/Строка/Ячейка/Токен` без изменения правил.
2. Перевести `KD-PE-105/106/107` на атрибутную модель.
3. Сделать реестр правил данными.
4. Добавить размеченный корпус и метрики.
5. Только затем — топология и нормативный каталог.

### 7.10. Чего не делать

- не переписывать конвейер целиком;
- не вводить числовые веса без корпуса;
- не выполнять автозамену обозначений;
- не повышать уровень замечания без доказательства;
- не смешивать извлечение и инженерный вывод.
